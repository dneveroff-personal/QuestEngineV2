# Concurrency Scenarios

Статус: 🟢 Accepted. Все 7 сценариев имеют решение; 5 из них (1, 2, 5, 6, 7) уже реализованы в коде и проверены тестами (включая реальные конкурентные IT-тесты, не только unit-моки).

## Назначение

Этот документ фиксирует ситуации гонки (race conditions) на уровне бизнес-правил — то есть случаи, когда два независимых действия, произошедшие «одновременно» (в один и тот же короткий промежуток времени, возможно с двух разных инстансов приложения или просто с двух параллельных HTTP-запросов), могут привести к нарушению инварианта, описанного в `01-domain/invariants.md`.

Инфраструктурный механизм защиты от гонок, связанных именно с планировщиком (Job 1/Job 2), описан в `03-architecture/scheduling.md`. Здесь — сценарии, связанные с действиями пользователей (авторов, капитанов, команд).

Каждый сценарий описан по схеме: **Инвариант под угрозой → Сценарий → Текущее состояние в коде → Требуемое решение**.

## Сценарий 1 — Превышение лимита команд при одновременном подтверждении

**Инвариант под угрозой** (`registration.md`): «Количество команд со статусом `APPROVED` не может превышать установленный лимит».

**Сценарий.**
У Quest установлен `maximumTeams = 20`. Уже подтверждено 19 команд. Два разных капитана регистрации одновременно нажимают «подтвердить» для двух разных заявок (или автор подтверждает две заявки почти одновременно, например, кликая по списку).

**Текущее состояние в коде — подтверждённая уязвимость.**

`QuestRegistrationServiceImpl.approveTeam()` выполняет проверку лимита так:

```java
private void validateApprovedTeamsLimit(Long questId) {
  long approvedCount = questRegistrationRepository.countByQuestIdAndStatus(questId, APPROVED);
  if (approvedCount >= quest.getMaximumTeams()) {
    throw new ForbiddenOperationException(...);
  }
}
```

Это классический паттерн **read-then-write без блокировки**: оба конкурентных запроса читают `approvedCount = 19`, оба видят `19 < 20`, оба проходят проверку, оба сохраняют `APPROVED`. Итог — 21 подтверждённая команда при лимите 20. Метод помечен `@Transactional`, но стандартный уровень изоляции транзакций (`READ COMMITTED` в PostgreSQL по умолчанию) **не предотвращает** этот сценарий — оба запроса читают committed-состояние «до» второго запроса.

**Требуемое решение.** Один из вариантов (нужен ADR):

- **Пессимистичная блокировка**: `SELECT ... FOR UPDATE` на строку Quest (или на агрегат «регистрации этого квеста») перед подсчётом — сериализует конкурентные `approveTeam()` для одного Quest.
- **Оптимистичная проверка через БД-constraint**: сложнее для условия "count ≤ N" (в отличие от `UNIQUE`, PostgreSQL не имеет декларативного "count constraint" из коробки без триггера) — потребовался бы `CHECK`-триггер, считающий `APPROVED`-регистрации при каждом INSERT/UPDATE. Более громоздко, но не блокирует конкурентные запросы искусственно.
- **Advisory lock PostgreSQL** (`pg_advisory_xact_lock(questId)`) вокруг проверки+записи — не требует блокировки самой строки Quest, что менее инвазивно для параллельных операций над разными частями того же Quest (например, редактирование уровня в этот момент не блокируется).

**Рекомендация**: пессимистичная блокировка через `SELECT ... FOR UPDATE` на строку `Quest` — самое простое и понятное решение, оправданное тем, что подтверждение заявок — не hot path (не сотни запросов в секунду), а разовое административное действие автора.

**Статус реализации**: решено — `QuestRepository.findByIdForUpdate` (`@Lock(PESSIMISTIC_WRITE)`), используется в `QuestRegistrationServiceImpl.validateApprovedTeamsLimit`. Проверено реальным конкурентным IT-тестом (`ApproveTeamRaceIT` — 10 потоков одновременно подтверждают заявки при лимите 3, итог всегда ровно 3 `APPROVED`).

## Сценарий 2 — Двойной вход команды в Quest (двойное создание первого LevelProgress)

**Инвариант под угрозой** (`progress.md`): «Первый LevelProgress создаётся в момент первого входа команды» — подразумевается ровно один раз.

**Сценарий.**
Участник команды открывает приложение на двух устройствах (телефон и планшет) одновременно и оба раза нажимает «войти в квест» почти одновременно (или клиент повторяет запрос из-за таймаута сети, не дождавшись ответа).

**Текущее состояние в коде.**

`QuestProgressServiceImpl.enterQuest()`:
```java
validateProgressWaiting(progress);       // читает status
progress.setStatus(RUNNING);             // пишет status
...
levelProgressService.createFirstLevelProgress(savedProgress.getId());
```

Тот же паттерн read-then-write: оба конкурентных вызова могут пройти `validateProgressWaiting` (оба видят `WAITING`), оба попытаются создать первый `LevelProgress`.

**Смягчающий фактор**: `V12__create_level_progress_table.sql` содержит `UNIQUE (quest_progress_id, level_id)` — второй `INSERT` физически упадёт на уровне БД. Это **предотвращает дублирование данных**, но не даёт корректный пользовательский результат — второй запрос получит необработанное исключение ограничения БД, а не осмысленный ответ вроде «уже начали» или идемпотентно тот же результат, что и первый запрос.

**Требуемое решение**: обернуть создание первого `LevelProgress` в обработку constraint violation → при перехвате возвращать уже существующий прогресс (то есть трактовать «уже начали» как успех, а не ошибку) — это правильная идемпотентная семантика для операции «войти в игру», где повторный вызов ожидаем (двойной клик, повтор запроса сетью).

**Статус реализации**: решено — `LevelProgressServiceImpl.createFirstLevelProgress`/`createNextLevelProgress` используют `saveAndFlush` + перехват `DataIntegrityViolationException`, возвращая существующую запись вместо ошибки. Проверено unit-тестами (`LevelProgressServiceImplTest`).

## Сценарий 3 — Повторный ввод BONUS/PENALTY-кода параллельно с двух устройств команды

**Инвариант под угрозой** (`bonus-penalty.md`, `code-submission.md`): один и тот же `BONUS`/`PENALTY`-код не должен засчитываться дважды одной команде.

**Сценарий.**
Два участника одной команды одновременно вводят один и тот же найденный бонус-код с двух разных телефонов (типичная ситуация в командной игре — все члены команды видят один код на карточке и вводят его "на всякий случай" одновременно).

**Текущее состояние в коде**: `CodeSubmission` как сущность не реализована (см. `code-submission.md`), поэтому механизм проверки «уже засчитан ли этот код для этого `LevelProgress`» пока не существует — фиксируется здесь заранее, на этапе проектирования, чтобы не повторить паттерн Сценариев 1–2.

**Требуемое решение (закладывается в дизайн `CodeSubmission` заранее)**: проверка «уже засчитан» и запись эффекта должны быть атомарны относительно параллельных попыток — на уровне БД это можно обеспечить через уникальный индекс `(level_progress_id, matched_code_id)` **для строк с результатом `CORRECT_*`** (частичный уникальный индекс в PostgreSQL, `WHERE result IN (...)`), а не только проверкой в коде перед сохранением — тот же паттерн read-then-write, что и в Сценариях 1–2, иначе будет воспроизведена та же уязвимость на новом месте.

## Сценарий 4 — Ручное начисление Bonus/Penalty автором одновременно с зачётом кода командой

**Инвариант под угрозой** (`bonus-penalty.md`): итоговое время — согласованный агрегат всех источников.

**Сценарий.**
Автор вручную начисляет команде штраф в тот же момент, когда команда вводит верный `BONUS`-код, зачитывающийся автоматически.

**Анализ**: в отличие от Сценариев 1–3, здесь **нет конфликта** по сути — оба события независимы и оба должны быть учтены, порядок их применения не важен, т.к. итоговое время по дизайну `bonus-penalty.md` — это **агрегат (сумма)** всех записей, а не единое перезаписываемое поле. Гонки не возникает, если реализация действительно суммирует записи `ManualTimeAdjustment` + `CodeSubmission` при каждом пересчёте, а не хранит и инкрементирует одно денормализованное число (`questProgress.bonusSeconds += X`), что как раз было бы уязвимо к потере обновления (lost update) при параллельной записи.

**Вывод**: этот сценарий не требует блокировок, но накладывает требование на реализацию — **не денормализовать** итоговое время в изменяемое поле, обновляемое инкрементом; агрегировать при чтении (или пересчитывать целиком при каждом изменении одного из слагаемых, что уже описано в `bonus-penalty.md`).

## Сценарий 5 — Параллельный автопереход и ручное завершение уровня в последний момент

**Инвариант под угрозой** (`progress.md`): «Одновременно у команды может быть только один активный LevelProgress».

**Сценарий.**
Время автоперехода уровня наступает (`autoTransitionAt` в прошлом) ровно в тот момент, когда команда вводит последний верный `MAIN`-код, завершающий уровень «честно». Job 2 планировщика (`03-architecture/scheduling.md`) и HTTP-запрос на ввод кода конкурируют за один и тот же `LevelProgress`.

**Требуемое решение**: оба пути завершения уровня (`CODES` и `AUTO_TRANSITION`, см. `progress.md`) должны переводить `LevelProgress` из `ACTIVE` в целевой статус через **условный UPDATE** (`WHERE status = 'ACTIVE'`), одинаково для обоих путей. Тот, кто «выигрывает» гонку — тот и определяет способ завершения (`CODES` или `AUTO_TRANSITION`) для этой записи; проигравшая сторона получает 0 обновлённых строк и должна трактовать это как «уровень уже завершён кем-то другим», не как ошибку. Прикладной эффект: если команда успела ввести код на миллисекунду раньше срабатывания планировщика — уровень честно засчитан как пройденный кодами, что корректно с точки зрения игрового смысла (команда реально успела).

**Статус реализации**: решено — `CodeSubmissionServiceImpl` использует `LevelProgressRepository.tryCompleteByCodesThreshold`, `LevelAutoTransitionScheduler` (Job 2) использует `LevelProgressRepository.tryAutoTransition` — оба условных UPDATE проверяют одно и то же `WHERE status = 'ACTIVE'`, гарантируя ровно один победивший путь. Проверено интеграционным тестом с реальной конкурентной гонкой (`LevelAutoTransitionRaceIT`).

## Сценарий 6 — Гонка при подсчёте порога решённых кодов под высокой параллельной нагрузкой

**Инвариант под угрозой** (ADR-0005): уровень завершается, когда количество различных решённых кодов достигает `Level.requiredMainCodesCount`.

**Контекст, отличающий этот сценарий от остальных**: продукт явно зафиксировал (`06-nfr/requirements.md`, «Внутрикомандный параллелизм ввода кода»), что команда может состоять из десятков игроков, параллельно вводящих коды на одном `LevelProgress`, и это **штатная, ожидаемая нагрузка**, а не редкий пограничный случай — в отличие от Сценариев 1–2 (разовые административные операции) и Сценария 3 (два устройства одного участника). Это меняет требование: нельзя просто "сериализовать доступ" через блокировку строки, аналогичную `SELECT ... FOR UPDATE` в ADR-0010 — при десятках конкурентных запросов в секунду на одну и ту же строку это создаст видимую задержку ответа именно в момент, когда скорость ответа — ключевое игровое качество.

**Сценарий.**
Порог уровня — 2 из 3 кодов. Уже решён 1 код. Два разных участника команды одновременно вводят синонимы двух **разных** оставшихся кодов (например, один вводит «декабрь», другой — «а», для кодов 2 и 3 соответственно). Оба запроса независимо проверяют «сколько кодов уже решено», оба видят «1 из 3», оба засчитывают свой код — но должен быть зафиксирован факт достижения порога (2 из 3) ровно один раз, и переход к следующему уровню должен быть инициирован ровно один раз, а не дважды параллельно (что воспроизвело бы Сценарий 5 — гонку за один и тот же `LevelProgress`).

**Требуемое решение**: подсчёт «сколько различных кодов решено» не должен выполняться как read-then-decide в коде приложения при высокой конкурентности. Вместо этого:
- Каждая успешная попытка (`CodeSubmission` с результатом `CORRECT_MAIN`) сохраняется независимо и быстро (не блокирующая операция, вставка новой строки — конкурентные `INSERT` в PostgreSQL не блокируют друг друга при отсутствии конфликтующих уникальных ограничений на разные `codeIndex`).
- Проверка «достигнут ли порог» и переход `LevelProgress → COMPLETED` выполняется как **условный UPDATE** (аналогично паттерну ADR-0010): `UPDATE level_progress SET status='COMPLETED' WHERE id=? AND status='ACTIVE' AND (SELECT COUNT(DISTINCT c.code_index) FROM code_submissions cs JOIN codes c ON c.id = cs.matched_code_id WHERE cs.level_progress_id=? AND cs.result='CORRECT_MAIN') >= required_count` — атомарно в рамках одного SQL-запроса, без предварительного чтения счётчика в коде приложения. Только тот запрос, который фактически довёл счётчик до порога, получает `0 → 1` обновлённую строку и инициирует переход к следующему уровню; остальные конкурентные вставки просто засчитывают свой код без побочного эффекта.
- Это устраняет необходимость в блокировке строки для самого частого, высоконагруженного пути (запись попытки) — блокировка/атомарность нужна только в момент перехода состояния, который происходит один раз за `LevelProgress`, а не на каждую попытку ввода.
- **Частичный индекс** `code_submissions(level_progress_id) WHERE result = 'CORRECT_MAIN'` — держит подзапрос быстрым независимо от количества **неверных** попыток на этом `LevelProgress` (которых, при отсутствии rate limiting, может быть сколь угодно много — см. `05-security/threat-model.md`). Индекс покрывает только строки с верным `MAIN`-результатом, их всегда мало (не больше числа кодов уровня).

### Масштаб за пределами одного LevelProgress (уточнено — национальный масштаб, см. `06-nfr/requirements.md`)

`WHERE id = :levelProgressId` в условном UPDATE блокирует **ровно одну строку**. Попытки команды A и команды B (тем более из разных городов, разных Quest) никогда не претендуют на одну и ту же строку — блокировок между ними нет вообще, независимо от того, сколько команд и городов играют параллельно. Паттерн, спроектированный для одной команды на одном уровне, автоматически работает и при 100 командах × 100 игроках × 10 городах одновременно — изоляция обеспечена на уровне данных (разные строки), не на уровне кода. Ограничивает такой масштаб пропускная способность инстанса приложения и БД в целом, а не корректность этого решения. Подробный разбор — `06-nfr/requirements.md`, «Национальный масштаб».

**Статус реализации**: решено — `LevelProgressRepository.tryCompleteByCodesThreshold` (миграция `V13`, частичный индекс `idx_code_submissions_lp_correct_main`). Проверено реальным конкурентным IT-тестом на 30 потоков (`CodeSubmissionControllerIT`).

## Сценарий 7 — Гонка между Job 1 (старт Quest) и `approveTeam()` "подтверждение после старта"

**Инвариант под угрозой**: `QuestProgress` для пары (Quest, Team) создаётся не более одного раза (уникальный индекс `(quest_id, team_id)`, `V11__create_quest_progress_table.sql`).

**Сценарий.**
Job 1 (`03-architecture/scheduling.md`) обрабатывает переход Quest в `RUNNING` и итерирует все `APPROVED`-регистрации, вызывая `questProgressService.createProgress(...)` для каждой команды. Параллельно администратор в этот же момент вызывает `approveTeam()` для ещё одной заявки — этот путь тоже вызывает `createProgress(...)` напрямую, если Quest уже `RUNNING` (веб "подтверждение после старта", `01-domain/registration.md`). Если оба пути обрабатывают одну и ту же команду в пересекающемся окне времени, `createProgress()` для одного из них завершится с ошибкой (нарушение уникального индекса).

**Требуемое решение**: Job 1 не должен прерывать всю пачку обработки квеста из-за одной команды, для которой `QuestProgress` уже создан параллельно. `createProgress()` бросает `IllegalArgumentException` на дубликат — Job 1 перехватывает это исключение для конкретной команды и переходит к следующей, трактуя это как «уже обработано кем-то другим», аналогично идемпотентной обработке в остальных сценариях.

**Статус реализации**: решено — `QuestStartScheduler.createProgressForApprovedTeams()` перехватывает `IllegalArgumentException` на уровне отдельной команды.

## Общий паттерн, повторяющийся во всех сценариях

Все найденные (Сценарий 1, 2) и спроектированные заранее (Сценарий 3, 5, 6) случаи — это один и тот же архитектурный анти-паттерн: **read-then-write без учёта конкурентного изменения между чтением и записью**, при часто присутствующем, но недостаточном `@Transactional` (изоляция `READ COMMITTED` его не решает). Сценарий 6 дополнительно показывает: под высокой конкурентной нагрузкой (десятки запросов/сек на одну строку) решение "просто заблокировать строку" само становится узким местом — лечится переносом самой проверки порога внутрь атомарного SQL-запроса, а не блокировкой на время всего цикла чтение-решение-запись в коде приложения.

**Рекомендация для code review будущих PR**: любой метод, который сначала проверяет условие (`count < limit`, `status == X`), а затем на основании этой проверки принимает решение сохранить/не сохранить — кандидат на этот класс багов и должен быть явно проверен на предмет конкурентного доступа при ревью, независимо от того, кажется ли сценарий "маловероятным".
