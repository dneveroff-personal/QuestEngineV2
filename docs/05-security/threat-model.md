# Threat Model

Статус: 🟢 Accepted. Дополняет `05-security/permissions.md` (ролевая модель "кто что может") — этот документ про "как это может быть обойдено технически" и что для этого нужно сделать. Все находки ниже имеют принятое решение (ADR-0011/0015/0016).

---

## Аутентификация

Модель — access + refresh токены (ADR-0015, заменяет первоначальный вариант «единый 24-часовой JWT + denylist»):

- **Access token** — JWT, HMAC (`io.jsonwebtoken`), 15 минут, используется для `Authorization: Bearer` на каждом запросе, полностью stateless.
- **Refresh token** — хранится в БД (хеш, не сырое значение), используется только через `POST /auth/refresh`, ротируется при каждом использовании (reuse detection).
- Пароли — `BCryptPasswordEncoder` (правильный выбор, соль встроена).
- Секрет JWT (`jwt.secret`) читается из переменных окружения, не захардкожен в `prod`. В `local`-профиле есть fallback-значение по умолчанию — приемлемо для разработки, но стоит явно предупредить: если `local`-профиль по ошибке окажется активен в реальном окружении, секрет будет публично известен (лежит в репозитории).

Полное обоснование модели — ADR-0015.

## Отзыв доступа (решено, ADR-0015)

Административный бан / logout / смена пароля отзывают все активные refresh-токены пользователя. Уже выданный access-токен продолжит действовать не дольше 15 минут (естественное истечение) — короткая, явно принятая задержка отзыва. Это заменяет прежнюю идею denylist для access-токенов — access-токен теперь не требует проверки по БД на каждый запрос вообще.

## Rate Limiting (решено, ADR-0016 — с важным уточнением по игровому геймплею)

Механизм — `bucket4j` (ADR-0016). Конкретные точки применения:

1. **`POST /auth/login`** — **5 попыток/минуту на IP**. Защита от перебора паролей.
2. **Ввод кода командой (`CodeSubmission`) — намеренно НЕ ограничивается rate limiting.** Это осознанное решение продукта, а не упущение: в команде может быть много участников (десятки), каждый может вводить коды параллельно, и **скорость — часть сути игры** (скорость чтения задания, скорость принятия решения, скорость ввода). Троттлинг по `LevelProgress`, который выглядел разумным по умолчанию (см. историю этого документа), был явно отклонён продуктом — он бы ограничивал легитимный геймплей, а не только атаку.

   Принятый компромисс: движок должен выдерживать высокую частоту легитимных попыток ввода (десятки параллельных запросов на один `LevelProgress` в секунду — реальный, ожидаемый паттерн нагрузки, не аномалия). Защита от автоматизированного перебора кодов достигается не троттлингом, а другими средствами:
   - Полный аудит всех попыток (`CodeSubmission`, включая неверные) — позволяет автору **постфактум** увидеть аномальный паттерн (например, тысячи попыток за секунды с одного `LevelProgress`, явно не соответствующие ручному вводу) и принять решение (дисквалификация команды, `ManualTimeAdjustment`-штраф) — детективный, а не превентивный контроль.
   - Ответственность за длину/сложность кода (устойчивость к простому перебору) — на авторе контента при создании `Code`, не на движке.
   - Общая защита от объёмной DoS-атаки (не специфичная для перебора кодов) — на уровне инфраструктуры (reverse proxy/firewall), вне scope доменной документации.
3. **`POST /auth/reset-admin-password`** — защищён заголовком `X-Admin-Secret`, сравниваемым через `String.equals()` — не timing-safe. Низкий приоритет (не hot path), заменить на `MessageDigest.isEqual()` при следующей правке `AuthController`.

## CORS (решено — простой сценарий)

Принято простое решение по умолчанию для текущего этапа: **фронтенд и API работают за одним общим reverse-proxy/доменом** (same-origin) — явная настройка `CorsConfiguration` не требуется, браузерная same-origin политика не создаёт препятствий.

Схема деплоя, которая на момент принятия этого решения ещё не была определена, теперь зафиксирована в `08-ops/deployment.md`: nginx как единственная публичная точка входа, backend не публикуется наружу напрямую. Это same-origin решение реализовано, а не только предположено — `CorsConfiguration` по-прежнему не требуется ни в проде, ни в dev-режиме (см. `08-ops/deployment.md`, раздел "Локальная разработка").

Если в будущем появится причина развернуть frontend на действительно отдельном домене (например, отдельный хостинг вроде Vercel/Netlify) — это будет пересмотром уже принятого решения в `08-ops/deployment.md`, а не продолжением этого пункта, и потребует явного whitelist origin'ов (не `*`, т.к. используется `Authorization`-заголовок).

## Доверие ко времени клиента

Общий принцип, уже частично зафиксированный в других документах, здесь — сводная формулировка как требование безопасности:

- **Сервер никогда не доверяет времени, присланному клиентом.** Ни один эндпоинт не должен принимать `timestamp`/`submittedAt` и т.п. полем запроса для операций, влияющих на честность игры — сервер всегда использует собственное `now()` в момент обработки. Это уже подразумевается в `hint-progress.md` («сервер сам решает, наступило ли время, не доверяя клиенту») и должно применяться так же к вводу кодов (`code-submission.md`), автопереходам (`scheduling.md`) — фиксируется здесь как сквозное правило, а не решение для одной фичи.

## Авторизация на уровне ресурсов (IDOR)

Общий принцип для code review, не найденная конкретная уязвимость: каждый эндпоинт, принимающий `{questId}`/`{teamId}`/`{levelId}` в пути, должен проверять не только "залогинен ли пользователь", но и "имеет ли он полномочие именно на этот конкретный ресурс" (например, `validateQuestAuthor` уже используется в нескольких местах — важно, чтобы этот паттерн был единообразным для всех мутирующих операций, включая ещё не реализованные `CodeSubmission`/`HintProgress`/`ManualTimeAdjustment`).

## Аудируемость административных действий

Уже зафиксировано как обязательное требование в `bonus-penalty.md` (ручные начисления бонуса/штрафа обязаны сохраняться как отдельные записи с `reason`/`createdBy`, а не перезаписывать число). Здесь подтверждается как часть общей модели угроз: соревновательная механика без аудита начислений — репутационный и юридический риск (оспаривание результатов), не только техническая недоработка. Аудит попыток ввода кода (см. Rate Limiting выше) — та же логика, применённая к другому классу действий.

## Открытые вопросы

Нет открытых архитектурных вопросов — все решения приняты (ADR-0011, ADR-0015, ADR-0016). Единственная мелкая техническая задача низкого приоритета: замена `String.equals()` на `MessageDigest.isEqual()` для сравнения `X-Admin-Secret` при следующей правке `AuthController`.
