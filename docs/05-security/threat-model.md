# Threat Model

Статус: 🟡 Draft. Дополняет `05-security/permissions.md` (ролевая модель "кто что может") — этот документ про "как это может быть обойдено технически" и что для этого нужно сделать.

---

## Аутентификация — что реализовано

- JWT, подписанный HMAC (`io.jsonwebtoken`, `Keys.hmacShaKeyFor`), передаётся как `Authorization: Bearer <token>`.
- Время жизни токена: `jwt.expiration` = `86400000` мс = **24 часа** (одинаково в `local` и `prod` профилях).
- Пароли — `BCryptPasswordEncoder` (правильный выбор, соль встроена, cost factor по умолчанию).
- Секрет JWT (`jwt.secret`) и секрет сброса пароля админа (`admin.reset.secret`) читаются из переменных окружения (`.env.example` их перечисляет) — не захардкожены в `prod`-профиле. В `local`-профиле есть fallback-значение по умолчанию (`OMGItsQuestEngineV2JWT...`) — приемлемо для локальной разработки, но стоит явно предупредить: если `local`-профиль когда-либо по ошибке окажется активен в реальном окружении, секрет будет публично известен (лежит в репозитории).

## Находка 1 — Токен нельзя отозвать раньше срока (24 часа)

JWT в текущей реализации — **чистый stateless-токен**: сервер не хранит список выданных/отозванных токенов, валидность проверяется только подписью и `expiration`. Это стандартный компромисс stateless JWT, но для соревновательной игры он имеет конкретное прикладное последствие:

**Сценарий**: во время игры обнаружено, что участник читерит (например, делится токеном с человеком вне команды, или получен через утечку). Прямо сейчас **нет способа принудительно разлогинить** этого пользователя раньше, чем истекут 24 часа — единственная мера — сменить пароль (не помогает, если токен уже выдан и активен) или сменить `jwt.secret` глобально (разлогинивает *всех* пользователей системы, а не одного — неприемлемо для эксплуатации).

**Требуется решение**: если сценарий "забанить одного участника посреди игры" важен для продукта — нужен механизм отзыва (например, denylist отозванных токенов/`jti` в Redis/БД с TTL до истечения токена, проверяемый в `JwtAuthFilter`). Если сценарий не считается критичным (например, потому что бан участника — редкое ручное административное действие, которое можно решить дисквалификацией команды в статистике, а не технической блокировкой доступа) — явно зафиксировать это как принятый риск, не требующий немедленной реализации.

## Находка 2 — Ни одного механизма rate limiting в проекте

Поиск по кодовой базе и `build.gradle.kts` не нашёл ни одной библиотеки для ограничения частоты запросов (`bucket4j`, `resilience4j-ratelimiter` и т.п.), ни собственной реализации. Это релевантно для нескольких конкретных точек:

1. **`POST /auth/login`** — без rate limiting уязвим к перебору паролей (credential stuffing / brute force). Особенно важно, т.к. `resetAdminPassword` в `AuthController` защищён отдельным секретом, но сам `login` — нет.
2. **Будущий ввод кодов командой** (`code-submission.md`) — уже отмечено в том документе как открытый вопрос, но фиксируется здесь как часть общей картины: короткие игровые коды особенно уязвимы к перебору без ограничения.
3. **`POST /auth/reset-admin-password`** — защищён заголовком `X-Admin-Secret`, сравниваемым через `String.equals()`. Это не timing-safe сравнение (в теории уязвимо к timing-атаке, определяющей секрет по времени ответа посимвольно) — на практике риск невысокий для одного административного эндпоинта, не вызываемого массово, но стоит заменить на `MessageDigest.isEqual()` при следующей правке файла как best practice, а не потому что это критично прямо сейчас.

**Требуется решение**: выбрать библиотеку (рекомендация: `bucket4j` — стандартный выбор для Spring, работает как per-IP/per-user лимитер на уровне фильтра) и хотя бы для `login` внедрить до первого публичного релиза. Для будущего `CodeSubmission` — требование уже зафиксировано в `code-submission.md`, здесь просто подтверждается как единая задача (не заводить два разных механизма rate limiting для разных частей системы).

## Находка 3 — CORS не сконфигурирован

Поиск `CorsConfiguration`/`@CrossOrigin` в кодовой базе не дал результатов — CORS не настроен явно нигде. Для stateless API с `Authorization: Bearer` (а не cookie-based сессией) это **менее рискованно**, чем для cookie-аутентификации (CSRF-класс атак здесь не применим напрямую — токен не отправляется браузером автоматически), но если веб-фронтенд будет обращаться к API с другого origin (типичная ситуация — SPA на одном домене, API на другом/поддомене), запросы из браузера будут блокироваться браузерной same-origin политikой без explicit CORS-заголовков, и разработчики обнаружат это только в интеграции, а не в спецификации.

**Требуется решение**: явно сконфигурировать разрешённые origin (whitelist, не `*`, т.к. используется `Authorization`-заголовок) как часть настройки, а не оставлять на "заработает само" — зафиксировать здесь как задачу для этапа интеграции с фронтендом, не для домена/бэкенда самого по себе.

## Доверие ко времени клиента

Общий принцип, уже частично зафиксированный в других документах, здесь — сводная формулировка как требование безопасности:

- **Сервер никогда не доверяет времени, присланному клиентом.** Ни один эндпоинт не должен принимать `timestamp`/`submittedAt` и т.п. полем запроса для операций, влияющих на честность игры — сервер всегда использует собственное `now()` в момент обработки. Это уже подразумевается в `hint-progress.md` («сервер сам решает, наступило ли время, не доверяя клиенту») и должно применяться так же к вводу кодов (`code-submission.md`), автопереходам (`scheduling.md`) — фиксируется здесь как сквозное правило, а не решение для одной фичи.

## Авторизация на уровне ресурсов (IDOR)

Общий принцип для code review, не найденная конкретная уязвимость (не проверялся построчно каждый эндпоинт в рамках этого документа, но фиксируется как чеклист): каждый эндпоинт, принимающий `{questId}`/`{teamId}`/`{levelId}` в пути, должен проверять не только "залогинен ли пользователь", но и "имеет ли он полномочие именно на этот конкретный ресурс" (например, `validateQuestAuthor` уже используется в нескольких местах — важно, чтобы этот паттерн был единообразным для всех мутирующих операций, включая ещё не реализованные `CodeSubmission`/`HintProgress`/`ManualTimeAdjustment`).

## Аудируемость административных действий

Уже зафиксировано как обязательное требование в `bonus-penalty.md` (ручные начисления бонуса/штрафа обязаны сохраняться как отдельные записи с `reason`/`createdBy`, а не перезаписывать число). Здесь подтверждается как часть общей модели угроз: соревновательная механика без аудита начислений — репутационный и юридический риск (оспаривание результатов), не только техническая недоработка.

## Открытые вопросы (требуют решения)

1. Нужен ли механизм отзыва JWT раньше истечения срока (Находка 1) — зависит от того, насколько критичен сценарий "забанить читера посреди игры".
2. Выбор и внедрение rate limiting (Находка 2) — как минимум для `/auth/login`, до первого релиза.
3. Явная настройка CORS (Находка 3) — на этапе интеграции с фронтендом.
4. Замена `String.equals()` на timing-safe сравнение для `X-Admin-Secret` — низкий приоритет, но стоит сделать при следующей правке `AuthController`.
