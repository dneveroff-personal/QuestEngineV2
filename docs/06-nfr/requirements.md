# Non-Functional Requirements

## Транспорт для live-статистики

`01-domain/statistics-ranking.md` требует: «Статистика должна обновляться автоматически. Каждое изменение QuestProgress должно приводить к пересчёту текущего положения команд.» — но не указывает, **как** это доставляется клиенту. Кода нет вообще (`statistic/` пуст, см. `04-api/endpoints.md`).

### Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Polling** (клиент опрашивает `GET /statistics` раз в N секунд) | Проще всего реализовать и отладить; не требует держать соединение | Задержка отображения = интервал опроса; лишняя нагрузка на сервер от множества клиентов, опрашивающих одновременно |
| **SSE** (Server-Sent Events) | Однонаправленный поток, простой протокол поверх HTTP, хорошо ложится на "сервер сообщает об изменениях" | Не работает "из коробки" через некоторые прокси/балансировщики без настройки; менее гибок, чем WebSocket, если позже понадобится двусторонний канал |
| **WebSocket** | Полный дуплекс, минимальная задержка, best practice для realtime UI | Больше инфраструктурной сложности (управление соединениями, реконнект, масштабирование на несколько инстансов требует sticky sessions или pub/sub-брокера) |

**Рекомендация**: **SSE** для MVP — статистика идёт строго в одном направлении (сервер → клиент), WebSocket даёт возможности, которые сейчас не нужны (клиент ничего не отправляет через тот же канал), а polling создаёт either задержку, либо лишнюю нагрузку при попытке её уменьшить. SSE также проще совместить с уже выбранным стеком (обычный `HttpServletResponse`/`ResponseBodyEmitter` в Spring MVC, без дополнительной библиотеки).

Решено (ADR-0014): SSE отправляет обновление немедленно при каждом изменении `QuestProgress`, без искусственной задержки/батчинга — согласуется с общим приоритетом проекта на скорость.

## Часовые пояса (ADR-0013 — решено)

- `Quest.startTime`, все runtime-timestamp'ы — `Instant` в Java, `TIMESTAMP WITH TIME ZONE` в PostgreSQL (см. миграции). Расчёты всегда в UTC.
- Отображение: `Quest.startTime` всегда показывается в часовом поясе устройства пользователя (браузер/клиентское приложение) — единообразно для всех форматов игры, т.к. ADR-0019 не вводит структурного различия офлайн/онлайн. Дополнительное поле часового пояса на Quest не требуется.
- Реализуется полностью на клиенте, сервер изменений не требует.

## Нагрузка

### Внутрикомандный параллелизм ввода кода (решено — ключевое требование)

Явно зафиксировано продуктом: одна команда может состоять из **десятков игроков** (например, 50), каждый из которых может параллельно вводить коды на одном и том же активном `LevelProgress` — и это ожидаемый, штатный паттерн, а не пиковая аномалия. **Скорость — часть сути игры**: скорость чтения задания, скорость принятия решения, скорость ввода кода. Это прямо повлияло на решение не вводить rate limiting для ввода кода (см. `05-security/threat-model.md`, `01-domain/code-submission.md`).

Практическое следствие для реализации `CodeSubmission`: запись попытки ввода кода и проверка/агрегация решённых кодов (ADR-0005) должны выдерживать десятки конкурентных записей в секунду **на один и тот же `LevelProgress`** без деградации и без гонок (см. также `02-processes/concurrency-scenarios.md` — при реализации `CodeSubmission` понадобится отдельный сценарий именно на этот случай, не только на «двойной клик одного участника»).

### Остальные параметры нагрузки

Не оценены с той же точностью:
- Сколько одновременно `RUNNING` Quest ожидается в пике (единицы? десятки? сотни)?
- Сколько команд в одном Quest в среднем/максимум (`Quest.maximumTeams` по умолчанию 100 — это ориентир, но не подтверждённое реальностью число)?
- Ожидается ли всплеск нагрузки в момент старта Quest (все команды одновременно нажимают «войти» в 21:00:00) — важно для `scheduling.md` Job 1 и для `enterQuest()`.

Рабочее предположение до уточнения: «десятки одновременных Quest, сотни команд, десятки игроков на команду с параллельным вводом кода» — этого достаточно, чтобы архитектурные решения (polling-планировщик, отсутствие rate limiting на ввод кода) были обоснованы для заявленной цели проекта («развернуть в интернете и проводить реальные квесты»), не для промышленного масштаба.

## Точность автоматизации (решено)

Интервал polling планировщика (`03-architecture/scheduling.md`, Job 1/Job 2) — **1 секунда**. Максимально чёткое из предложенных значений, выбрано осознанно: соответствует общему приоритету проекта на скорость и точность игрового времени (см. также решение не троттлить ввод кода — «скорость — часть сути игры»). Проверяемое NFR: «Quest должен перейти в RUNNING не позднее чем через 1 секунду после `startTime`»; аналогично для автоперехода уровня.

## Локализация / язык (решено — только русский в MVP)

Захардкоженные русскоязычные сообщения об ошибках (`"Квест не найден: "` и т.п. — уже около 20 штук в сервисах) остаются как есть, без рефакторинга на `MessageSource`. Осознанное решение продукта: не тратить время на i18n в MVP — движок ориентирован на русскоязычную аудиторию на этом этапе.

Если мультиязычность понадобится позже — рефакторинг на `MessageSource` неизбежен, и чем больше сообщений накопится к тому моменту, тем он дороже. Это принятый компромисс, а не забытый риск.

## Доступность / отказоустойчивость (решено — single-instance в MVP)

**MVP разворачивается в единственном экземпляре приложения.** ShedLock (распределённая блокировка планировщика, `scheduling.md`) откладывается — не нужен, пока нет multi-instance деплоя.

Тем не менее сохраняется требование: "сервис может быть перезапущен в любой момент во время `RUNNING` Quest без потери или дублирования игровых данных" — обеспечивается идемпотентным дизайном планировщика (условные UPDATE, см. ADR-0010 и `scheduling.md`), которое реализуется независимо от того, single- или multi-instance деплой. Это значит, что переход на multi-instance в будущем (если понадобится) не потребует переделки самой бизнес-логики — только добавления ShedLock поверх уже идемпотентного кода.

## Открытые вопросы (требуют решения)

1. Транспорт live-статистики — SSE выбран (ADR-0014), требует реализации.
2. Порядок величины нагрузки (Quest/команды одновременно) — вопрос к продукту/бизнесу, не техническое решение. Ориентир для учебного проекта — единицы одновременных Quest, десятки команд (соответствует масштабу «разместить в интернете и проводить реальные квесты» как целевому уровню, не промышленной нагрузке).
3. Допустимая задержка срабатывания планировщика — конкретное число.
4. Требуется ли i18n сообщений об ошибках, или зафиксировать русский язык как единственный.
5. Требования к отказоустойчивости (single vs multi-instance в MVP) — для учебного проекта на первом этапе (модульный монолит) разумно принять single-instance как достаточный, с идемпотентным дизайном (см. `scheduling.md`), готовым к multi-instance без переделки, когда/если появится необходимость.

Часовой пояс отображения (`Quest.startTime`) — решён, см. выше (ADR-0013).
