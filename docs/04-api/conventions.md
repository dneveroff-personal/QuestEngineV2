# API Conventions

Статус: 🟡 Draft. Часть решений уже де-факто принята в коде (и здесь просто зафиксирована как контракт), часть — расхождения, найденные при сверке кода, требующие решения.

Этот документ — соглашения, общие для всех REST-ресурсов. Конкретные ресурсы/эндпоинты — в `04-api/endpoints.md`.

Источник истины для полного списка полей запросов/ответов — сгенерированная OpenAPI-спека (`springdoc-openapi` уже подключён, доступна по `/api-docs`, UI — `/swagger-ui`). Этот документ не дублирует её, а фиксирует **соглашения**, которые OpenAPI не выражает (семантику кодов ошибок, версионирование, пагинацию и т.п.).

## Формат ошибок

Уже реализовано и работает хорошо: `GlobalExceptionHandler` использует **RFC 7807 `ProblemDetail`** — это правильный, стандартный подход, фиксируем его как обязательный контракт для всех будущих ошибок API (в том числе тех, что появятся вместе с `CodeSubmission`, планировщиком и т.д. — не изобретать новый формат ошибок).

Форма ответа об ошибке:

```json
{
  "type": "https://api.questenginev2.dn/problems/forbidden-operation",
  "title": "Forbidden Operation",
  "status": 409,
  "detail": "Действие доступно только Автору квеста",
  "instance": "/api/quests/42/progress",
  "timestamp": "2026-08-18T10:15:30Z"
}
```

Поле `errors` (список `{field, message}`) добавляется дополнительно для ошибок валидации (`MethodArgumentNotValidException`, `ConstraintViolationException`).

### ⚠️ Найденные несоответствия кода ошибок HTTP-статусам

При чтении `GlobalExceptionHandler` найдено два случая, где смысл исключения не соответствует выбранному HTTP-статусу — семантически некорректно, хотя технически работает:

1. **`ForbiddenOperationException` → `409 Conflict`.** Название исключения говорит "запрещено" (ожидался бы `403 Forbidden`), а обработчик возвращает `409 Conflict`. `403` означает «у вас нет прав на это действие» (проблема авторизации), `409` означает «действие противоречит текущему состоянию ресурса» (например, нельзя одобрить уже одобренную заявку). Судя по местам использования в коде (`validateQuestAuthor`, `validateApprovedTeamsLimit`, `validateProgressWaiting`) — исключение сейчас используется **для обоих смыслов одновременно**, что и есть корень проблемы.

2. **`IllegalArgumentException`/`IllegalStateException` → `409 Conflict`.** Стандартная семантика этих Java-исключений ближе к `400 Bad Request` (некорректные входные данные / некорректное состояние объекта для операции), но в проекте они массово используются и для случаев "сущность не найдена" (`"Квест не найден: " + questId` — это должно быть `404 Not Found`, не `409`/`400`).

**Требуется решение** (ADR или просто согласованный рефакторинг): развести семантику на три независимых случая с тремя разными статусами:
- `403 Forbidden` — у пользователя нет прав на действие в принципе (роль/владение).
- `409 Conflict` — у пользователя есть права, но текущее состояние ресурса не позволяет действие (уже одобрено, лимит достигнут, квест уже завершён).
- `404 Not Found` — сущность с данным ID не существует (сейчас часто кидается как `IllegalArgumentException` вместо специализированного `NotFoundException`, что и приводит к неверному статусу).

Это не блокер для документации API-контракта первой версии (можно зафиксировать текущее поведение "as is" и исправить отдельным рефакторингом), но обязательно к решению, т.к. клиентский код (мобильное приложение/веб) должен уметь различать «нет прав» от «уже нельзя» от «не найдено» программно, а не по тексту `detail`.

## Аутентификация (решено — ADR-0015)

`Authorization: Bearer <access token>` на каждом API-запросе. Access-токен — JWT, 15 минут, stateless. Обновление — `POST /auth/refresh` с refresh-токеном (хранится в БД, ротируется при каждом использовании). Публичные без токена: `/api/auth/**`, Swagger/OpenAPI-эндпоинты, `/actuator/**`.

Клиент обязан реализовать перехват `401` от истёкшего access-токена → вызов `/auth/refresh` → повтор исходного запроса с новым токеном — стандартный паттерн для этой модели.

## Версионирование

Все ресурсы сейчас находятся под `/api/...` **без номера версии** (`Routes.API = "/api"`). Это осознанное решение или временное — не зафиксировано нигде.

**Требуется решение.** Рекомендация для проекта на раннем этапе: не вводить версионирование в URL (`/api/v1/...`) искусственно, пока нет второго клиента с несовместимыми ожиданиями — но **зафиксировать это как сознательное решение**, а не умолчание, чтобы не столкнуться с breaking change без стратегии миграции, когда придёт время. Если/когда потребуется версионирование — предпочтителен путь в URL (`/api/v2/...`) как самый явный и кэш-дружественный вариант, а не versioning через заголовки.

## Пагинация

### ⚠️ Найденная неполнота реализации

Ряд эндпоинтов (`GET /api/users`, `GET /api/teams`) уже принимают `Pageable` (стандартный Spring-механизм — `?page=0&size=20&sort=...`), но методы сервисов возвращают **`List<...>`, а не `Page<...>`**. Это значит, что параметры пагинации на вход **принимаются и используются** (отрезают нужную страницу данных из БД), но клиент **не получает** в ответе метаданные — общее количество записей, общее количество страниц, есть ли следующая страница. Клиент, получивший 20 записей, не может отличить «это ровно все записи» от «есть ещё, долистай».

**Требуется решение**: заменить `List<T>` на `Page<T>` (или свою DTO-обёртку `{content, totalElements, totalPages, page, size}`, если не хотим протекать Spring Data-типы в контракт API напрямую — что обычно и является лучшей практикой, чтобы не завязывать публичный контракт на конкретную реализацию пагинации). Второй вариант предпочтительнее для стабильности контракта.

Эндпоинты без пагинации вообще (`GET /api/quests/authors/{authorId}`, `GET .../progress` по Quest) — открытый вопрос, нужна ли она сейчас, учитывая ожидаемые объёмы (см. `06-nfr/requirements.md`).

## Формат даты и времени

`Instant` (Java) сериализуется в ISO-8601 UTC (`"2026-08-18T21:00:00Z"`) — стандартное поведение Jackson по умолчанию для `Instant`, уже используется во всех DTO (`QuestResponse.startTime` и т.п.). Фиксируем как обязательное правило для всех новых полей с датой/временем: **всегда `Instant`, никогда `LocalDateTime`** без явной зоны — `LocalDateTime` неоднозначен относительно часового пояса и уже привёл бы к путанице в игре, где честность игрового времени — ключевое свойство (см. ADR-002). Единственное текущее исключение — `LocalDateTime.now()` в `GlobalExceptionHandler` для поля `timestamp` в теле ошибки; стоит привести к единообразию с `Instant` при следующей правке этого файла.

Связанный открытый вопрос про отображение времени в часовом поясе пользователя — вынесен в `06-nfr/requirements.md`.

## Идемпотентность мутирующих запросов

Не описано нигде и не гарантируется единообразно (см. также подтверждённые находки в `02-processes/concurrency-scenarios.md`, Сценарии 1–2). Общее правило, которое стоит принять для всех новых эндпоинтов: `POST`-запросы, создающие runtime-факт по действию пользователя, который **разумно ожидать повторно** (двойной клик, повтор из-за таймаута сети) — например, «войти в квест», «ввести код» — должны быть либо естественно идемпотентны (повторный вызов не создаёт дубликата и возвращает тот же результат), либо явно защищены от дублирования на уровне БД (уникальный индекс), а не полагаться только на проверку в коде сервиса.
