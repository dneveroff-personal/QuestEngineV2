# API Conventions

Статус: 🟡 Draft. Часть решений уже де-факто принята в коде (и здесь просто зафиксирована как контракт), часть — расхождения, найденные при сверке кода, требующие решения.

Этот документ — соглашения, общие для всех REST-ресурсов. Конкретные ресурсы/эндпоинты — в `04-api/endpoints.md`.

Источник истины для полного списка полей запросов/ответов — сгенерированная OpenAPI-спека (`springdoc-openapi` уже подключён, доступна по `/api-docs`, UI — `/swagger-ui`). Этот документ не дублирует её, а фиксирует **соглашения**, которые OpenAPI не выражает (семантику кодов ошибок, версионирование, пагинацию и т.п.).

---

## Формат ошибок

`GlobalExceptionHandler` использует **RFC 7807 `ProblemDetail`** — обязательный контракт для всех ошибок API.

Форма ответа об ошибке:

```json
{
  "type": "https://api.questenginev2.dn/problems/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "…",
  "instance": "/api/…",
  "timestamp": "2026-08-18T10:15:30Z"
}
```

`timestamp` — `Instant` (ISO-8601 UTC).

## HTTP-статусы (решено — ADR-0011)

- `400` — синтаксическая/валидационная ошибка запроса;
- `401` — нет или невалидный токен;
- `403` — аутентифицирован, но нет права;
- `404` — ресурс не найден;
- `409` — конфликт состояния (в т.ч. бизнес-инварианты: аномальный уровень, недостижимый `requiredMainCodesCount`, повторная регистрация и т.п.);
- `500` — непредвиденная ошибка сервера.

## Пагинация (решено и реализовано — ADR-0012)

Своя DTO-обёртка `PageResponse<T>` (`{content, page, size, totalElements, totalPages}`), а не проброс Spring Data `Page<T>` напрямую в контракт — чтобы не завязывать публичный API на конкретную реализацию пагинации. Реализовано на `/api/users/search` и `/api/teams/search` (единственные два listing-эндпоинта, уже принимавшие `Pageable`). Тестов пока нет (пишутся отдельно).

Эндпоинты без пагинации вообще (`GET /api/quests/authors/{authorId}`, `GET .../progress` по Quest) — открытый вопрос, нужна ли она сейчас, учитывая ожидаемые объёмы (см. `06-nfr/requirements.md`).

## Формат даты и времени

`Instant` (Java) сериализуется в ISO-8601 UTC (`"2026-08-18T21:00:00Z"`) — стандартное поведение Jackson по умолчанию для `Instant`, уже используется во всех DTO (`QuestResponse.startTime` и т.п.). Фиксируем как обязательное правило для всех новых полей с датой/временем: **всегда `Instant`, никогда `LocalDateTime`** без явной зоны — `LocalDateTime` неоднозначен относительно часового пояса и уже привёл бы к путанице в игре, где честность игрового времени — ключевое свойство (см. ADR-002). Поле `timestamp` в теле ошибки (`GlobalExceptionHandler`) тоже использует `Instant.now()` — единообразие с DTO.

Связанный открытый вопрос про отображение времени в часовом поясе пользователя — вынесен в `06-nfr/requirements.md`.

## Идемпотентность мутирующих запросов

Не описано нигде и не гарантируется единообразно (см. также подтверждённые находки в `02-processes/concurrency-scenarios.md`, Сценарии 1–2). Общее правило, которое стоит принять для всех новых эндпоинтов: `POST`-запросы, создающие runtime-факт по действию пользователя, который **разумно ожидать повторно** (двойной клик, повтор из-за таймаута сети) — например, «войти в квест», «ввести код» — должны быть либо естественно идемпотентны (повторный вызов не создаёт дубликата и возвращает тот же результат), либо явно защищены от дублирования на уровне БД (уникальный индекс), а не полагаться только на проверку в коде сервиса.

## Открытые вопросы (требуют решения)

Нет открытых вопросов — все решения приняты (ADR-0011, ADR-0012, ADR-0015). Версионирование URL — сознательно не вводится, пока нет второго клиента с несовместимыми ожиданиями (см. выше). Оставшееся — задачи реализации (рефакторинг статусов ошибок, `Page<T>`), отслеживаются в `roadmap/backlog.md`, не архитектурные развилки.
