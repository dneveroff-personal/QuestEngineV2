# Code Submission

Статус: 🟡 Draft. Содержит открытые вопросы (см. раздел «Открытые вопросы»), требующие решения перед реализацией.

## Назначение

`CodeSubmission` — факт попытки команды ввести код на активном уровне (`LevelProgress`).
Это runtime-событие игрового процесса: команда играет и вводит коды, которые придумал автор Quest на этапе редактирования (`Code`, см. `03-architecture/domain-model.md`).

На момент написания этого документа в системе реализовано только редактирование `Code` автором (CRUD в `code/service`). Игровая механика ввода кода командой — **не реализована**, это документ-спецификация для будущей разработки.

---

## Участники и контекст

- Код вводится **в контексте активного `LevelProgress`** конкретной команды. Ввод кода вне активного уровня невозможен: нет активного уровня → нет возможности вводить коды.
- Ввести код может **любой участник команды**, а не только капитан. Капитанские полномочия (см. `01-domain/team.md`) относятся к управлению составом и заявками, а не к игровому процессу — ввод кодов является совместной игровой активностью, а не административным действием.
- Author и Admin **не вводят коды** — они управляют их набором на этапе редактирования Level.

---

## Откуда берутся «правильные» коды

Коды `Code` привязаны к `Level` (не к `LevelProgress`), у каждого кода есть `type` (`MAIN` / `BONUS` / `PENALTY`) и `value`.

Проверка введённого значения выполняется относительно набора `Code`, принадлежащих текущему активному `Level` команды: `code.level.id == activeLevelProgress.level.id`.

### ⚠️ Существующая проблема в реализации, которую нужно решить

`CodeServiceImpl.validateCodeValueUnique` в текущем коде проверяет уникальность `code_value` **глобально по всей базе**, а не в пределах одного `Level`. Это означает, что одинаковый код (например, `"1234"`) нельзя использовать на двух разных уровнях — даже в разных Quest разных авторов. Это ограничивает авторов и не соответствует практике движков этого класса (Encounter и аналоги допускают повторяющиеся коды между уровнями/квестами).

**Требуется решение** (зафиксировать в ADR): либо
1. уникальность `code_value` **в пределах одного Level** (`level_id + code_value`), либо
2. уникальность полностью отключить — коды на разных уровнях могут совпадать, дубликат на одном уровне — ошибка.

Рекомендация: вариант (1), проверка на дубликаты остаётся только внутри `level_id`.

## Нормализация введённого значения

Открытый вопрос, но необходимо явное решение до реализации ввода:

- **Регистр**: сравнение регистронезависимое (`"CactuS" == "cactus"`) — стандартная практика Encounter-подобных движков, т.к. команды часто вводят код с телефона, где автоввод меняет регистр.
- **Пробелы**: значение обрезается (`trim`) по краям перед сравнением. Внутренние пробелы не удаляются (иначе `"12 34"` совпадёт с `"1234"`, что может быть нежелательно).
- Оба правила применяются одинаково и к `value`, сохранённому автором, и к введённому командой значению — сравнение через нормализованные строки, оригинал (`value`) не изменяется в БД.

## Типы кодов и их эффект при вводе

| Тип | Эффект при верном вводе |
|---|---|
| `MAIN` | Засчитывается как успешное прохождение уровня. Открывается следующий Level (если это не последний), либо Quest считается пройденным (если это последний Level). |
| `BONUS` | **Не завершает уровень.** Начисляет бонусное время команде (см. `bonus-penalty.md`). Уровень остаётся активным, команда продолжает вводить коды. |
| `PENALTY` | **Не завершает уровень.** Начисляет штрафное время команде (см. `bonus-penalty.md`). Уровень остаётся активным. |

### Условие завершения уровня по кодам

`progress.md` описывает завершение уровня как «команда ввела необходимое количество правильных кодов» — формулировка сама по себе неоднозначна, а модель данных (`Level`) сейчас не содержит поля вроде `requiredMainCodesCount`.

**Требуется явное решение.** Два возможных варианта:

- **Вариант A (рекомендуется, соответствует классике Encounter)**: у уровня может быть несколько `MAIN`-кодов — это синонимы одного правильного ответа (например, "МОСКВА" и "MOSCOW" как два принятых варианта). Достаточно ввести **любой один** `MAIN`-код, чтобы завершить уровень. `points` у `MAIN`-кода в этом случае не используется (или зарезервирован под будущий scoring-режим).
- **Вариант B**: уровень требует ввода **всех** `MAIN`-кодов (составная загадка из нескольких частей, каждая — отдельный код). Тогда действительно нужен подсчёт «необходимого количества».

До принятия решения (см. ADR) реализация не должна начинаться — от выбора варианта зависит форма `LevelProgress` (нужен ли список уже введённых `MAIN`-кодов) и UX подсказки прогресса команде («введено 2 из 3»).

## CodeSubmission как runtime-сущность (проектируемая модель)

Не существует в коде, потребуется для аудита, статистики попыток и антибрутфорс-защиты.

Предполагаемые поля:

- `id`
- `levelProgress` (ManyToOne → на каком именно прохождении уровня сделана попытка)
- `submittedBy` (ManyToOne → User, кто из участников команды ввёл код — для истории, не для прав)
- `rawValue` (что фактически ввели, до нормализации — важно для отладки и разбора спорных ситуаций)
- `matchedCode` (ManyToOne → Code, nullable; null, если ни один код на уровне не совпал)
- `result` (enum: `CORRECT_MAIN`, `CORRECT_BONUS`, `CORRECT_PENALTY`, `INCORRECT`)
- `submittedAt`

Каждая попытка ввода — **отдельная запись**, включая неверные попытки. Без хранения неверных попыток невозможны: антибрутфорс, отображение статистики «сколько попыток потратила команда», разбор споров после игры.

## Anti-bruteforce / rate limiting

Открытый вопрос, требует решения на этапе `05-security/threat-model.md`, но фиксируем здесь как игровое правило:

- Короткие коды (частая практика — 4–6 символов) уязвимы к перебору. Без ограничения команда может отправлять сотни попыток в минуту программно (не вручную).
- Предлагается: **троттлинг по `LevelProgress`** — не более N попыток в интервал времени (например, 1 попытка в 2 секунды), с явным ответом об ожидании, а не тихим отбрасыванием запроса.
- Троттлинг не должен мешать честной игре (ручной ввод одной командой редко превышает 1 попытку в несколько секунд), но должен останавливать автоматизированный перебор.
- Требует финального решения о конкретных числах — вне scope этого документа, фиксируется в NFR/threat-model.

## Повторный ввод уже принятого кода

- Повторный ввод уже засчитанного `MAIN`-кода на том же `LevelProgress` — идемпотентен: не создаёт повторного эффекта (уровень уже завершён, ввод кодов для него более невозможен, т.к. активного `LevelProgress` для этого уровня уже нет).
- Повторный ввод уже засчитанного `BONUS`/`PENALTY`-кода **в рамках одного и того же уровня одной командой** — **не повторяет начисление**. Каждый `BONUS`/`PENALTY`-код команда может конвертировать в эффект только один раз за прохождение (иначе команда, узнавшая бонус-код, может обналичивать его бесконечно, отправляя его повторно). Технически: перед применением эффекта нужно проверить, есть ли уже `CodeSubmission` с этим `matchedCode` для этого `LevelProgress`/`QuestProgress` и результатом `CORRECT_*`.

## Открытые вопросы (требуют решения до реализации)

1. Уникальность `code_value`: глобально или в пределах Level (см. выше — рекомендация дана).
2. Вариант A/B завершения уровня по кодам (один любой MAIN vs все MAIN) — блокирует модель `LevelProgress`.
3. Единица измерения `Code.points` для `BONUS`/`PENALTY` — минуты или секунды (см. `bonus-penalty.md`).
4. Конкретные числа rate limiting (попыток/интервал).
5. Публикуется ли команде статистика попыток других команд (например, «сколько попыток у лидера») — влияет на честность соревнования.
