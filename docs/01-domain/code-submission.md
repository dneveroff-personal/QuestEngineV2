# Code Submission

Статус: 🟢 Accepted. Модель (типы уровней, коды, синонимы, порог) зафиксирована ADR-0004/ADR-0005/ADR-0006. Открытых вопросов не осталось.

## Назначение

`CodeSubmission` — факт попытки команды ввести код на активном уровне (`LevelProgress`).
Это runtime-событие игрового процесса: команда играет и вводит коды, которые придумал автор Quest на этапе редактирования (`Code`, см. `03-architecture/domain-model.md`).

На момент написания этого документа в системе реализовано только редактирование `Code` автором (CRUD в `code/service`), а также — заранее, до `CodeSubmission` — оркестрация завершения уровня и перехода к следующему (`LevelProgressServiceImpl.completeLevel`, `QuestProgressServiceImpl.completeLevel`), пока вызываемая только напрямую, без API-эндпоинта и без привязки к вводу кода. Сам ввод кода командой — **не реализован**.

---

## Терминология (ADR-0005)

- **Код** — логический правильный ответ уровня.
- **Синоним** — конкретный принятый вариант написания этого кода. Технически — строка `Code` с типом `MAIN`; несколько синонимов одного кода объединены общим `Code.codeIndex`. Ввод любого синонима засчитывает **весь код**.
- `BONUS`/`PENALTY`-коды не являются «требуемыми кодами» уровня, `codeIndex` для них не применяется.

---

## Участники и контекст

- Код вводится **в контексте активного `LevelProgress`** конкретной команды. Ввод кода вне активного уровня невозможен: нет активного уровня → нет возможности вводить коды.
- Ввести код может **любой участник команды**, а не только капитан. Капитанские полномочия (см. `01-domain/team.md`) относятся к управлению составом и заявками, а не к игровому процессу — ввод кодов является совместной игровой активностью, а не административным действием.
- Author и Admin **не вводят коды** — они управляют их набором на этапе редактирования Level.

---

## Уникальность кода (ADR-0004)

Уникальность `code_value` проверяется **в пределах одного Level** (`level_id + code_value`), а не глобально по всей базе. Полное обоснование — ADR-0004.

---

## Нормализация введённого значения

- **Регистр**: сравнение регистронезависимое (`"CactuS" == "cactus"`) — команды часто вводят код с телефона, где автоввод меняет регистр.
- **Пробелы**: значение обрезается (`trim`) по краям перед сравнением. Внутренние пробелы не удаляются (иначе `"12 34"` совпадёт с `"1234"`, что может быть нежелательно).
- Оба правила применяются одинаково и к `value`, сохранённому автором, и к введённому командой значению — сравнение через нормализованные строки, оригинал (`value`) не изменяется в БД.

## Модель завершения уровня (ADR-0005)

Полное обоснование модели — ADR-0005. Здесь — прикладные правила для реализации ввода кода.

### Таксономия уровней

| Тип | Коды | Автопереход | Как проходится |
|---|---|---|---|
| Аномальный | нет | нет | Непроходим. Ошибка конфигурации автора, должна отклоняться при публикации. |
| Заглушка по времени | нет | да | Только автопереходом. |
| Заглушка по коду | 1 код, без синонимов | нет | Только вводом кода (либо DNF). |
| Обычный | 1 код (возможно с синонимами) | да | Кодом или автопереходом — что наступит раньше. |
| Составной | несколько кодов, у каждого возможны синонимы | не важно | Автор задаёт порог — сколько кодов нужно решить. |

### Порог

`Level.requiredMainCodesCount` (nullable Integer):
- `null` — требуются **все** коды уровня.
- число `N` — уровень завершается, как только команда решит **любые N различных кодов** из имеющихся на уровне (порядок решения не важен).

### Условие завершения уровня по кодам

Уровень переходит в `COMPLETED` (способ `CODES`), когда количество различных решённых кодов (различных `codeIndex` с зачтённым синонимом) на этом `LevelProgress` достигает `Level.requiredMainCodesCount` (или общего числа кодов уровня, если порог не задан).

### Прогресс, показываемый команде (решено)

Во время игры команда видит текст вида **«Осталось ввести {remaining} из {requiredMainCodesCount} кодов»**, где `remaining = requiredMainCodesCount − количество уже решённых кодов` (или из общего числа кодов уровня, если порог не задан). Показывается именно «осталось», а не «решено» — команде важнее знать, сколько ещё нужно, чем сколько уже сделано.

---

## Типы кодов и их эффект при вводе

| Тип | Эффект при верном вводе |
|---|---|
| `MAIN` (синоним кода, определяемого `codeIndex`) | Засчитывает свой код как решённый. Если после этого достигнут порог — уровень завершается способом `CODES` (см. `03-architecture/scheduling.md`, Job 2 и `QuestProgressServiceImpl.completeLevel`, который открывает следующий Level либо переводит `QuestProgress` в `FINISHED`, если это был последний Level — см. ADR-0009). Если порог ещё не достигнут — уровень остаётся активным, команда продолжает вводить коды. |
| `BONUS` | **Не завершает уровень и не входит в подсчёт порога.** Начисляет бонусное время команде (см. `bonus-penalty.md`). |
| `PENALTY` | **Не завершает уровень и не входит в подсчёт порога.** Начисляет штрафное время команде (см. `bonus-penalty.md`). |

## CodeSubmission как runtime-сущность (проектируемая модель)

Не существует в коде, потребуется для аудита, статистики попыток, антибрутфорс-защиты и подсчёта решённых кодов.

Предполагаемые поля:

- `id`
- `levelProgress` (ManyToOne → на каком именно прохождении уровня сделана попытка)
- `submittedBy` (ManyToOne → User, кто из участников команды ввёл код — для истории, не для прав)
- `rawValue` (что фактически ввели, до нормализации — важно для отладки и разбора спорных ситуаций)
- `matchedCode` (ManyToOne → Code, nullable; null, если ни один код на уровне не совпал)
- `result` (enum: `CORRECT_MAIN`, `CORRECT_BONUS`, `CORRECT_PENALTY`, `INCORRECT`)
- `submittedAt`

Каждая попытка ввода — **отдельная запись**, включая неверные попытки. Без хранения неверных попыток невозможны: антибрутфорс-аудит, отображение статистики «сколько попыток потратила команда», разбор споров после игры, подсчёт решённых кодов (количество различных `matchedCode.codeIndex` среди `CORRECT_MAIN`-записей текущего `LevelProgress`).

Под ожидаемую нагрузку (см. ниже — десятки конкурентных попыток в секунду на один `LevelProgress`) переход `LevelProgress → COMPLETED` при достижении порога должен реализовываться атомарным условным UPDATE, а не read-then-write в коде приложения — см. `02-processes/concurrency-scenarios.md`, Сценарий 6.

## Anti-bruteforce / rate limiting (решено — намеренно НЕ ограничивается)

**Ввод кода командой не ограничивается rate limiting.** Осознанное решение продукта: в команде может быть много участников (десятки), каждый может вводить коды параллельно, и скорость — часть сути игры (скорость чтения задания, принятия решения, ввода). Троттлинг по `LevelProgress` рассматривался как защита по умолчанию, но явно отклонён — он ограничивал бы легитимный геймплей, а не только атаку.

Движок должен выдерживать высокую частоту легитимных попыток — десятки параллельных запросов на один `LevelProgress` в секунду это ожидаемый паттерн нагрузки, не аномалия (см. `06-nfr/requirements.md`, «Нагрузка»). Проверяется целевым k6-смок-тестом (`07-quality/testing-strategy.md`).

Защита от автоматизированного перебора (в отличие от честной параллельной игры многих людей) — не троттлингом, а иначе:
- Полный аудит всех попыток (`CodeSubmission`, включая неверные) — позволяет автору постфактум увидеть аномальный паттерн и принять решение (дисквалификация, `ManualTimeAdjustment`-штраф) — детективный, а не превентивный контроль.
- Ответственность за длину/сложность кода — на авторе контента.

Полное обоснование — `05-security/threat-model.md`, раздел «Rate Limiting».

## Повторный ввод уже принятого кода

- Повторный ввод синонима уже решённого кода на том же `LevelProgress` — идемпотентен: код уже засчитан, повторный ввод не создаёт нового эффекта (но может быть залогирован как `CodeSubmission` для полноты истории).
- Повторный ввод уже засчитанного `BONUS`/`PENALTY`-кода **в рамках одного и того же уровня одной командой** — **не повторяет начисление**. Каждый `BONUS`/`PENALTY`-код команда может конвертировать в эффект только один раз за прохождение (иначе команда, узнавшая бонус-код, может обналичивать его бесконечно, отправляя его повторно). Технически: перед применением эффекта нужно проверить, есть ли уже `CodeSubmission` с этим `matchedCode` для этого `LevelProgress`/`QuestProgress` и результатом `CORRECT_*`.

## Видимость статистики попыток (решено)

См. `01-domain/statistics-ranking.md` — автору доступна полная статистика попыток всех команд; команде — только собственная статистика попыток на текущем активном уровне, без данных других команд.
