# Code Submission

Статус: 🟢 Accepted. Модель (типы уровней, коды, синонимы, порог) зафиксирована ADR-0004/ADR-0005/ADR-0006. Открытых вопросов по доменной модели нет.

## Назначение

`CodeSubmission` — факт попытки команды ввести код на активном уровне (`LevelProgress`).
Это runtime-событие игрового процесса: команда играет и вводит коды, которые придумал автор Quest на этапе редактирования (`Code`, см. `03-architecture/domain-model.md`).

**Runtime-механика реализована.** Команда может отправить код через `POST /api/quests/progress/{questId}/{teamId}/codes`. Каждая попытка сохраняется как `CodeSubmission`; корректный `MAIN`-код может атомарно завершить уровень и запустить дальнейшую оркестрацию QuestProgress. Реализация покрыта unit/controller/IT и конкурентными тестами.

---

## Терминология (ADR-0005)

- **Код** — логический правильный ответ уровня.
- **Синоним** — конкретный принятый вариант написания этого кода. Технически — строка `Code` с типом `MAIN`; несколько синонимов одного кода объединены общим `Code.codeIndex`. Ввод любого синонима засчитывает **весь код**.
- `BONUS`/`PENALTY`-коды не являются «требуемыми кодами» уровня, `codeIndex` для них не применяется.

---

## Участники и контекст

- Код вводится **в контексте активного `LevelProgress`** конкретной команды. Ввод кода вне активного уровня невозможен: нет активного уровня → нет возможности вводить коды.
- Ввести код может **любой участник команды**, а не только капитан. Капитанские полномочия относятся к управлению составом и заявками, а не к игровому процессу.
- Author и Admin **не вводят коды** — они управляют их набором на этапе редактирования Level.

---

## Уникальность кода (ADR-0004)

Уникальность `code_value` проверяется **в пределах одного Level** (`level_id + code_value`), а не глобально по всей базе. Полное обоснование — ADR-0004.

---

## Нормализация введённого значения

- **Регистр**: сравнение регистронезависимое.
- **Пробелы**: значение обрезается (`trim`) по краям перед сравнением. Внутренние пробелы не удаляются.
- Оригинал введённого значения (`rawValue`) сохраняется в БД.

## Модель завершения уровня (ADR-0005)

### Таксономия уровней

| Тип | Коды | Автопереход | Как проходится |
|---|---|---|---|
| Аномальный | нет | нет | Непроходим. Ошибка конфигурации автора, должна отклоняться при публикации. |
| Заглушка по времени | нет | да | Только автопереходом. |
| Заглушка по коду | 1 код, без синонимов | нет | Только вводом кода (либо DNF). |
| Обычный | 1 код (возможно с синонимами) | да | Кодом или автопереходом — что наступит раньше. |
| Составной | несколько кодов, у каждого возможны синонимы | не важно | Автор задаёт порог — сколько кодов нужно решить. |

### Порог

`Level.requiredMainCodesCount` (nullable Integer):
- `null` — требуются **все** коды уровня.
- число `N` — уровень завершается, как только команда решит **любые N различных кодов** из имеющихся на уровне.

### Условие завершения уровня по кодам

Уровень переходит в `COMPLETED` (способ `CODES`), когда количество различных решённых кодов (различных `codeIndex` с зачтённым синонимом) на этом `LevelProgress` достигает `Level.requiredMainCodesCount` (или общего числа кодов уровня, если порог не задан).

### Прогресс, показываемый команде

Команда видит текст вида **«Осталось ввести {remaining} из {requiredMainCodesCount} кодов»**, где `remaining = requiredMainCodesCount − количество уже решённых кодов` (или из общего числа кодов уровня, если порог не задан).

## Типы кодов и их эффект при вводе

| Тип | Эффект при верном вводе |
|---|---|
| `MAIN` | Засчитывает свой код как решённый. Если достигнут порог — уровень завершается способом `CODES` и запускается дальнейшая оркестрация QuestProgress. |
| `BONUS` | Не завершает уровень и не входит в подсчёт порога. Начисляет бонусное время команде (см. `bonus-penalty.md`). |
| `PENALTY` | Не завершает уровень и не входит в подсчёт порога. Начисляет штрафное время команде (см. `bonus-penalty.md`). |

## CodeSubmission как runtime-сущность

`CodeSubmission` реализован как runtime-аудит попыток.

Поля:

- `id`
- `levelProgress`
- `submittedBy`
- `rawValue`
- `matchedCode` (nullable при несовпадении)
- `result` (`CORRECT_MAIN`, `CORRECT_BONUS`, `CORRECT_PENALTY`, `INCORRECT`)
- `submittedAt`

Каждая попытка ввода — **отдельная запись**, включая неверные попытки. Это обеспечивает аудит и будущую статистику попыток.

Переход `LevelProgress → COMPLETED` при достижении порога реализован через атомарный условный UPDATE — см. `02-processes/concurrency-scenarios.md`, Сценарий 6.

## Anti-bruteforce / rate limiting (решено — намеренно НЕ ограничивается)

**Ввод кода командой не ограничивается rate limiting.** В команде может быть много участников, каждый может вводить коды параллельно, и скорость — часть сути игры.

Движок должен выдерживать высокую частоту легитимных попыток. Проверка целевой нагрузки выполняется k6-смок-тестом (`07-quality/testing-strategy.md`).

Защита от автоматизированного перебора — не троттлингом CodeSubmission, а полным аудитом попыток и последующим fair-play контролем.

---

## Повторный ввод уже принятого кода

- Повторный ввод синонима уже решённого кода на том же `LevelProgress` — идемпотентен: код уже засчитан, повторный ввод не создаёт нового эффекта (но может быть залогирован как `CodeSubmission`).
- Повторный ввод уже засчитанного `BONUS`/`PENALTY`-кода **в рамках одного и того же уровня одной командой** — не должен повторять начисление. Каждый такой код должен конвертироваться в эффект только один раз за прохождение. Реализацию этого ограничения необходимо отдельно проверить тестом.

## Открытые вопросы

По доменной модели открытых вопросов нет. Runtime-повтор после потери соединения и одноразовое применение BONUS/PENALTY-кода должны быть проверены на уровне фактической реализации и тестов.
