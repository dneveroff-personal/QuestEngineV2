# Code Submission

Статус: 🟡 Draft. Основная модель (типы уровней, группы кодов, порог) зафиксирована ADR-0004/ADR-0005/ADR-0006 — Accepted. Остаются открытые вопросы по деталям реализации (см. раздел ниже).

## Назначение

`CodeSubmission` — факт попытки команды ввести код на активном уровне (`LevelProgress`).
Это runtime-событие игрового процесса: команда играет и вводит коды, которые придумал автор Quest на этапе редактирования (`Code`, см. `03-architecture/domain-model.md`).

На момент написания этого документа в системе реализовано только редактирование `Code` автором (CRUD в `code/service`), а также — заранее, до `CodeSubmission` — оркестрация завершения уровня и перехода к следующему (`LevelProgressServiceImpl.completeLevel`, `QuestProgressServiceImpl.completeLevel`), пока вызываемая только напрямую, без API-эндпоинта и без привязки к вводу кода. Сам ввод кода командой — **не реализован**.

---

## Участники и контекст

- Код вводится **в контексте активного `LevelProgress`** конкретной команды. Ввод кода вне активного уровня невозможен: нет активного уровня → нет возможности вводить коды.
- Ввести код может **любой участник команды**, а не только капитан. Капитанские полномочия (см. `01-domain/team.md`) относятся к управлению составом и заявками, а не к игровому процессу — ввод кодов является совместной игровой активностью, а не административным действием.
- Author и Admin **не вводят коды** — они управляют их набором на этапе редактирования Level.

---

## Уникальность кода (ADR-0004)

Уникальность `code_value` проверяется **в пределах одного Level** (`level_id + code_value`), а не глобально по всей базе. Полное обоснование — ADR-0004.

---

## Нормализация введённого значения

- **Регистр**: сравнение регистронезависимое (`"CactuS" == "cactus"`) — команды часто вводят код с телефона, где автоввод меняет регистр.
- **Пробелы**: значение обрезается (`trim`) по краям перед сравнением. Внутренние пробелы не удаляются (иначе `"12 34"` совпадёт с `"1234"`, что может быть нежелательно).
- Оба правила применяются одинаково и к `value`, сохранённому автором, и к введённому командой значению — сравнение через нормализованные строки, оригинал (`value`) не изменяется в БД.

## Модель завершения уровня (ADR-0005) — main-коды, синонимы, порог

Полное обоснование модели — ADR-0005. Здесь — прикладные правила для реализации ввода кода.

### Таксономия уровней

| Тип | Коды | Автопереход | Как проходится |
|---|---|---|---|
| Аномальный | нет | нет | Непроходим. Ошибка конфигурации автора, должна отклоняться при публикации. |
| Заглушка по времени | нет | да | Только автопереходом. |
| Заглушка по коду | 1 main-код, без синонимов | нет | Только вводом кода (либо DNF). |
| Обычный | 1 main-код (возможно с синонимами) | да | Кодом или автопереходом — что наступит раньше. |
| Составной | несколько main-кодов, у каждого возможны синонимы | не важно | Автор задаёт порог — сколько из main-кодов нужно решить. |

### Группы кодов (синонимы)

Коды на уровне с типом `MAIN` группируются: коды с одинаковым `groupIndex` — синонимы одного и того же смыслового ответа. Ввод **любого одного** синонима засчитывает всю группу как решённую. `BONUS`/`PENALTY`-коды в группировку не входят.

### Порог

`Level.requiredMainCodesCount` (nullable Integer):
- `null` — требуются **все** группы main-кодов уровня (для «обычного» уровня с одной группой это означает «единственная группа», для составного без явного порога — «все части»).
- число `N` — уровень завершается, как только команда решит **любые N различных групп** из имеющихся на уровне (порядок решения групп значения не имеет).

### Условие завершения уровня по кодам

Уровень переходит в `COMPLETED` (способ `CODES`), когда количество различных решённых group на этом `LevelProgress` достигает `Level.requiredMainCodesCount` (или общего числа групп, если порог не задан).

## Типы кодов и их эффект при вводе

| Тип | Эффект при верном вводе |
|---|---|
| `MAIN` (в составе своей группы `groupIndex`) | Засчитывает свою группу как решённую. Если после этого достигнут порог — уровень завершается способом `CODES` (см. `03-architecture/scheduling.md`, Job 2 и `QuestProgressServiceImpl.completeLevel`, который открывает следующий Level либо переводит `QuestProgress` в `FINISHED`, если это был последний Level — см. ADR-0009). Если порог ещё не достигнут — уровень остаётся активным, команда продолжает вводить коды. |
| `BONUS` | **Не завершает уровень и не входит в подсчёт порога.** Начисляет бонусное время команде (см. `bonus-penalty.md`). |
| `PENALTY` | **Не завершает уровень и не входит в подсчёт порога.** Начисляет штрафное время команде (см. `bonus-penalty.md`). |

## CodeSubmission как runtime-сущность (проектируемая модель)

Не существует в коде, потребуется для аудита, статистики попыток, антибрутфорс-защиты и подсчёта решённых групп.

Предполагаемые поля:

- `id`
- `levelProgress` (ManyToOne → на каком именно прохождении уровня сделана попытка)
- `submittedBy` (ManyToOne → User, кто из участников команды ввёл код — для истории, не для прав)
- `rawValue` (что фактически ввели, до нормализации — важно для отладки и разбора спорных ситуаций)
- `matchedCode` (ManyToOne → Code, nullable; null, если ни один код на уровне не совпал)
- `result` (enum: `CORRECT_MAIN`, `CORRECT_BONUS`, `CORRECT_PENALTY`, `INCORRECT`)
- `submittedAt`

Каждая попытка ввода — **отдельная запись**, включая неверные попытки. Без хранения неверных попыток невозможны: антибрутфорс, отображение статистики «сколько попыток потратила команда», разбор споров после игры, подсчёт решённых групп (количество различных `matchedCode.groupIndex` среди `CORRECT_MAIN`-записей текущего `LevelProgress`).

## Anti-bruteforce / rate limiting

Механизм выбран (ADR-0016 — `bucket4j`), конкретные числа для эндпоинта ввода кода — не зафиксированы этим документом, определяются при реализации совместно с `05-security/threat-model.md`:

- Короткие коды (частая практика — 4–6 символов) уязвимы к перебору. Без ограничения команда может отправлять сотни попыток в минуту программно (не вручную).
- Предлагается: троттлинг по `LevelProgress` — не более N попыток в интервал времени (например, 1 попытка в 2 секунды), с явным ответом об ожидании, а не тихим отбрасыванием запроса.
- Троттлинг не должен мешать честной игре (ручной ввод одной командой редко превышает 1 попытку в несколько секунд), но должен останавливать автоматизированный перебор.

## Повторный ввод уже принятого кода

- Повторный ввод синонима уже решённой группы на том же `LevelProgress` — идемпотентен: группа уже засчитана, повторный ввод не создаёт нового эффекта (но может быть залогирован как `CodeSubmission` для полноты истории).
- Повторный ввод уже засчитанного `BONUS`/`PENALTY`-кода **в рамках одного и того же уровня одной командой** — **не повторяет начисление**. Каждый `BONUS`/`PENALTY`-код команда может конвертировать в эффект только один раз за прохождение (иначе команда, узнавшая бонус-код, может обналичивать его бесконечно, отправляя его повторно). Технически: перед применением эффекта нужно проверить, есть ли уже `CodeSubmission` с этим `matchedCode` для этого `LevelProgress`/`QuestProgress` и результатом `CORRECT_*`.

## Открытые вопросы (требуют решения до реализации)

1. Конкретные числа rate limiting (попыток/интервал) — техническая деталь, не блокирует проектирование модели.
2. Публикуется ли команде статистика попыток других команд (например, «сколько попыток у лидера») — влияет на честность соревнования.
3. Нужна ли автору UI-подсказка прогресса «решено 2 из 3 групп» во время игры, или это раскрывало бы слишком много информации о структуре уровня.
