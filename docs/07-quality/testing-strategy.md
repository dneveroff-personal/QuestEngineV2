# Testing Strategy & Definition of Done

Статус: 🟡 Draft.

## Назначение

Зафиксировать то, что уже сложилось в проекте как устойчивый паттерн тестирования (чтобы новые фичи — `CodeSubmission`, `HintProgress`, планировщик — следовали ему осознанно, а не случайно), и закрыть пробелы, найденные при сверке.

---

## Существующий паттерн (уже устоялся, фиксируем как обязательный)

Для каждого ресурса в проекте устойчиво повторяется **три уровня теста**:

1. **`*ServiceImplTest`** — модульный тест сервиса с замоканным репозиторием (Mockito). Проверяет бизнес-логику и валидации изолированно.
2. **`*ControllerTest`** — `@WebMvcTest`-подобный тест контроллера с замоканным сервисом. Проверяет HTTP-слой: коды статусов, сериализацию, валидацию входных DTO.
3. **`*ControllerIT`** — полный интеграционный тест через `BaseIntegrationTest` (Testcontainers, `postgres:16-alpine`, реальная БД, реальный Spring-контекст). Проверяет, что всё вместе — контроллер, сервис, репозиторий, миграции Flyway — действительно работает.

Это правильная и достаточно редко встречающаяся на практике дисциплина — **закрепляем её явно как обязательный паттерн** для всех новых фич, включая ещё не реализованные `CodeSubmission`, `HintProgress`, `ManualTimeAdjustment`, Job 1/Job 2 планировщика, статистику.

## Найденные пробелы в существующем покрытии

1. **`JwtService` не имеет отдельного `JwtServiceTest`.** Проверяется только косвенно, через `LoginServiceImplTest`. Для компонента, отвечающего за генерацию и валидность токена (см. `05-security/threat-model.md`), стоит иметь прямой unit-тест: корректность `claims`, `expiration`, поведение при истёкшем токене.
2. **`GlobalExceptionHandler` не имеет отдельного теста**, который бы явно проверял соответствие типа исключения → HTTP-статуса для каждого случая. Именно этот класс сейчас содержит найденную в `04-api/conventions.md` неточность (`ForbiddenOperationException` → `409` вместо `403`) — отдельный тест на каждую пару "исключение → ожидаемый статус" сделал бы такие расхождения заметными сразу при код-ревью, а не только при чтении документации.
3. **Нет `jacocoTestCoverageVerification`.** JaCoCo подключён и генерирует отчёт (`build.gradle.kts`, `tasks.jacocoTestReport`), но нет задачи, которая бы **проваливала сборку** при недостаточном покрытии — отчёт можно посмотреть, но нельзя обеспечить, что он не деградирует со временем. См. рекомендацию ниже.

## Тестируемость time-based кода — уже частично решено, нужно продолжать

`LevelProgressServiceImpl` и `QuestProgressServiceImpl` уже используют **инъекцию `java.time.Clock`** вместо прямого вызова `Instant.now()` — это правильный паттерн, позволяющий детерминированно тестировать логику, зависящую от времени (например, «прошло ли `autoTransitionAt`»), подставляя фиксированный `Clock` в тестах вместо реального времени.

Однако `Instant.now()` вызывается напрямую (без инъекции `Clock`) ещё в **16 файлах**, включая как минимум один сервис, где это станет проблемой при следующей доработке — `QuestRegistrationServiceImpl` (потребует детерминированного времени при исправлении гонки из `concurrency-scenarios.md`, Сценарий 1, и вероятно при развитии в сторону автоматизации).

**Требование на будущее**: любой новый сервис, для которого текущее время влияет на бизнес-логику (а не только на `createdAt`/`updatedAt` audit-поля, где это не критично) — обязан принимать `Clock` через конструктор, а не вызывать `Instant.now()`/`System.currentTimeMillis()` напрямую. Это напрямую касается будущих `CodeSubmission` (см. `code-submission.md`), `HintProgress` (см. `hint-progress.md`) и Job 1/Job 2 планировщика (см. `scheduling.md`) — без этого требования их логику невозможно будет протестировать детерминированно (тесты, зависящие от реального `sleep()`, — известный источник нестабильных/медленных тестов, "flaky tests").

## Тестирование сценариев гонки (concurrency)

`02-processes/concurrency-scenarios.md` фиксирует 5 сценариев, 2 из которых — подтверждённые в текущем коде уязвимости (Сценарии 1, 2). Требование к их исправлению:

**Каждое исправление гонки обязано сопровождаться тестом, воспроизводящим саму гонку** (например, запуск N параллельных потоков/корутин, вызывающих `approveTeam()` одновременно, с проверкой, что итоговое количество `APPROVED`-регистраций не превышает лимит) — а не только тестом на "happy path" одного вызова. Тест на happy path не отличает исправленный код от неисправленного для этого класса багов — гонка по определению не проявляется в один поток.

## Definition of Done для новой фичи

Чек-лист, обязательный для любой новой фичи игровой механики (например, `CodeSubmission`) перед тем, как она считается завершённой:

- [ ] Написан/обновлён документ в `docs/`, статус поднят до 🟢 Accepted (открытые вопросы закрыты либо явно перенесены в `roadmap/backlog.md`).
- [ ] `*ServiceImplTest` — покрыты все ветки бизнес-валидации, включая граничные случаи из `01-domain/invariants.md`.
- [ ] `*ControllerTest` — покрыты коды ответов, включая ошибочные (используя корректную семантику `403`/`404`/`409` из `04-api/conventions.md`, а не автоматически `409` для всего).
- [ ] `*ControllerIT` — полный путь через реальную БД (Testcontainers).
- [ ] Если фича зависит от времени — используется инъекция `Clock`, есть тест с фиксированным временем на границе условия (например, ровно в момент `autoTransitionAt`, за секунду до и после).
- [ ] Если фича описана в `concurrency-scenarios.md` как подверженная гонке — есть тест, воспроизводящий параллельный доступ.
- [ ] Пройден `spotlessCheck` (Google Java Format, уже подключён как обязательный шаг перед `compileJava` — ломает сборку при нарушении форматирования, ничего дополнительно настраивать не нужно).
- [ ] `roadmap/backlog.md` обновлён — статус фичи переведён из ⚪/🟡 в 🔵 Implemented.

## Открытые вопросы (требуют решения)

1. Конкретное пороговое значение для `jacocoTestCoverageVerification` (например, 80% line coverage для `service`-пакетов) — число не выбрано, требует решения команды, не техническое ограничение.
2. Нужны ли нагрузочные тесты (JMeter/Gatling/k6) уже в MVP — зависит от ответа на вопрос о нагрузке в `06-nfr/requirements.md` (там же остаётся открытым).
3. Требуется ли contract-тестирование API (например, сверка ответов с OpenAPI-спекой автоматически) — пока не рассматривалось.
