# Testing Strategy & Definition of Done

Статус: 🟢 Accepted.

## Назначение

Зафиксировать то, что уже сложилось в проекте как устойчивый паттерн тестирования (чтобы новые фичи следовали ему осознанно), и закрыть пробелы, найденные при сверке.

---

## Существующий паттерн (уже устоялся, фиксируем как обязательный)

Для каждого ресурса в проекте устойчиво повторяется **три уровня теста**:

1. **`*ServiceImplTest`** — модульный тест сервиса с замоканным репозиторием (Mockito). Проверяет бизнес-логику и валидации изолированно.
2. **`*ControllerTest`** — `@WebMvcTest`-подобный тест контроллера с замоканным сервисом. Проверяет HTTP-слой: коды статусов, сериализацию, валидацию входных DTO.
3. **`*ControllerIT`** — полный интеграционный тест через `BaseIntegrationTest` (Testcontainers, `postgres:16-alpine`, реальная БД, реальный Spring-контекст). Проверяет, что всё вместе — контроллер, сервис, репозиторий, миграции Flyway — действительно работает.

Это правильная и достаточно редко встречающаяся на практике дисциплина — **закрепляем её явно как обязательный паттерн** для всех новых фич.

## Найденные пробелы в существующем покрытии

1. **`JwtService` не имеет отдельного `JwtServiceTest`.** Проверяется только косвенно, через `LoginServiceImplTest`. Для компонента, отвечающего за генерацию и валидность токена (см. `05-security/threat-model.md`), стоит иметь прямой unit-тест: корректность `claims`, `expiration`, поведение при истёкшем токене.
2. **`GlobalExceptionHandler` не имеет отдельного теста**, который бы явно проверял соответствие типа исключения → HTTP-статуса для каждого случая.
3. ~~Нет `jacocoTestCoverageVerification`.~~ **Решено (ADR-0017, amended):** жёсткий порог и fail-the-build по покрытию **не** вводятся. JaCoCo-отчёты остаются информационными (локально и как CI-артефакт).

## Тестируемость time-based кода — уже частично решено, нужно продолжать

`LevelProgressServiceImpl` и `QuestProgressServiceImpl` уже используют **инъекцию `java.time.Clock`** вместо прямого вызова `Instant.now()` — это правильный паттерн, позволяющий детерминированно тестировать логику, зависящую от времени.

**Требование на будущее**: любой новый сервис, для которого текущее время влияет на бизнес-логику (а не только на audit-поля `createdAt`/`updatedAt`) — обязан принимать `Clock` через конструктор. См. ADR-0018.

## Тестирование сценариев гонки (concurrency)

`02-processes/concurrency-scenarios.md` фиксирует сценарии гонок. Требование к исправлениям:

**Каждое исправление гонки обязано сопровождаться тестом, воспроизводящим саму гонку** (параллельные потоки), а не только happy-path одного вызова.

Сценарий 6 (порог кодов под параллельной нагрузкой) уже закрыт конкурентным IT-тестом; дополнительно есть **опциональный** k6-смок на уровне HTTP (см. ниже).

## Definition of Done для новой фичи

Чек-лист, обязательный для любой новой фичи игровой механики перед тем, как она считается завершённой:

- [ ] Написан/обновлён документ в `docs/`, статус поднят до 🟢 Accepted (открытые вопросы закрыты либо явно перенесены в `roadmap/backlog.md`).
- [ ] `*ServiceImplTest` — покрыты все ветки бизнес-валидации, включая граничные случаи из `01-domain/invariants.md`.
- [ ] `*ControllerTest` — покрыты коды ответов, включая ошибочные (семантика `403`/`404`/`409` из `04-api/conventions.md`).
- [ ] `*ControllerIT` — полный путь через реальную БД (Testcontainers).
- [ ] Если фича зависит от времени — используется инъекция `Clock`, есть тест с фиксированным временем на границе условия.
- [ ] Если фича описана в `concurrency-scenarios.md` как подверженная гонке — есть тест, воспроизводящий параллельный доступ.
- [ ] Пройден `spotlessCheck` (Google Java Format, уже обязательный шаг перед `compileJava`).
- [ ] `roadmap/backlog.md` обновлён — статус фичи переведён в 🔵 Implemented.

**Нет** требования «покрытие ≥ N%» и нет fail-the-build по JaCoCo (ADR-0017).

## Нагрузочное / смок-тестирование (решено)

### k6-смок на Сценарий 6 — опционально, не CI-gate

Уже есть конкурентный IT-тест (десятки потоков в одном JVM), который проверяет атомарность порога кодов. Он закрывает корректность логики.

k6 даёт **другой слой**: реальный HTTP, отдельные соединения, нагрузка ближе к «много клиентов». Это полезно как **ручной pre-release smoke**, а не как обязательный шаг каждого PR.

- Скрипт: `load-tests/k6/scenario6-code-threshold.js`
- Запуск: против поднятого локально/стейдж API (см. `load-tests/k6/README.md`)
- **Не** подключён как required check в `build.yml` — по желанию можно гонять вручную перед релизом

Полноценное performance-тестирование (JMeter/Gatling, SLA по latency) — не в scope MVP. Масштаб «100 команд × 100 игроков» — см. `06-nfr/requirements.md`, отдельный чек-лист перед национальным запуском.
