# Frontend Design System

## 1. Назначение

Design System определяет общий визуальный и UX-подход QuestEngine.

Главные цели:

- современный внешний вид;
- лаконичность;
- высокая читаемость;
- минимальное количество лишних действий;
- единообразие всех экранов;
- удобство использования с мобильных устройств;
- отдельный UX для игрового режима;
- возможность в дальнейшем менять визуальную тему без переработки компонентов.

Design System не определяет бизнес-логику.

Бизнес-правила определяются backend-документацией проекта.

---

# 2. Общий визуальный характер

QuestEngine должен выглядеть как современный продукт для сообщества игроков,
а не как корпоративная CRM или административная система.

Основные характеристики:

- clean;
- modern;
- compact;
- functional;
- readable;
- responsive.

Интерфейс должен отдавать приоритет информации и действиям,
а не декоративным элементам.

Не использовать:
- чрезмерные градиенты;
- большое количество декоративных элементов;
- тяжёлые визуальные эффекты;
- избыточные анимации;
- большие пустые области;
- интерфейс, перегруженный карточками;
- элементы, которые выглядят интерактивными, но ими не являются.

---

# 3. Принцип "Content First"

QuestEngine — информационно-игровое приложение.

Пользователь должен быстро понимать:

1. где он находится;
2. что сейчас происходит;
3. что он может сделать;
4. что произойдёт после действия.

Каждый экран должен иметь одно основное действие.

Например:

Quest:

> Подать заявку

Подтверждённая команда:

> Войти в игру

QuestProgress:

> Ввести код

LevelProgress:

> Продолжить

Не следует конкурировать несколькими равнозначными CTA.

---

# 4. Цветовая система

Цвета должны задаваться через semantic design tokens,
а не напрямую в компонентах.

Используется система CSS variables.

Основные semantic tokens:

```text
background
foreground

card
card-foreground

primary
primary-foreground

secondary
secondary-foreground

muted
muted-foreground

accent
accent-foreground

destructive
destructive-foreground

border
input
ring
```

Конкретные значения цветов не должны быть жёстко зашиты в отдельных React-компонентах.

Это позволит изменить тему приложения централизованно.

---

# 5. Семантические цвета статусов

Статусы должны иметь не только цвет,
но и текстовое обозначение или другой визуальный идентификатор.

Цвет никогда не является единственным способом передачи информации.

## Success
Используется для:
* успешного ввода кода;
* подтверждённой заявки;
* завершённого уровня;
* финиша команды.


## Warning
Используется для:
* ожидания подтверждения;
* приближения автоперехода;
* предупреждений.


## Destructive
Используется для:
* ошибок;
* отклонённых действий;
* штрафных действий;
* потенциально опасных операций.

## Muted
Используется для:
* второстепенной информации;
* неактивных состояний;
* завершённых или архивных данных.

--- 

# 6. Типографика

Основной приоритет:
1. читаемость;
2. визуальная иерархия;
3. компактность.

Не следует использовать большое количество размеров шрифта.

Основные уровни:

```text
Display
H1
H2
H3
Body
Small
Caption
```

Заголовки должны использоваться для создания структуры страницы, а не как декоративные элементы.

Основной текст должен быть комфортно читаемым как на desktop, так и на мобильном устройстве.

---

# 7. Layout

Основной интерфейс использует ограниченную ширину контента.

На широких экранах контент не должен растягиваться на всю ширину viewport.

Рекомендуемый принцип:

```text
┌──────────────────────────────────────────┐
│ Header                                   │
├──────────────────────────────────────────┤
│                                          │
│        Main Content                      │
│                                          │
│        max-width container               │
│                                          │
└──────────────────────────────────────────┘
```
На мобильных устройствах:
```text
┌──────────────────┐
│ Header            │
├──────────────────┤
│                  │
│ Content          │
│                  │
│                  │
└──────────────────┘
```

Контент должен адаптироваться без горизонтального скролла.

---

# 8. Navigation

Основная навигация должна быть минимальной.

Для обычного игрока:

```text
Мои квесты
Команда
Профиль
```

Для автора дополнительно:

> Авторская

Для администратора доступны все соответствующие разделы.

Ролевые различия должны выражаться прежде всего доступностью действий,
а не созданием нескольких разных интерфейсов.

---

# 9. Quest Card

Карточка Quest используется:
* на главной странице;
* в списках квестов;
* в "Моих квестах";
* в авторской части.

Минимально отображает:

* название;
* дату и время старта;
* тип;
* автора;
* состояние;
* краткую информацию.

Карточка должна иметь одно очевидное действие или открывать страницу Quest.

Не следует помещать в карточку большое количество информации.

---

# 10. Quest Page

Страница Quest является информационной страницей.

Основной порядок:
```text
Название
↓
Основная информация
↓
Описание
↓
Участники
↓
Действие пользователя
```

Для пользователя действие зависит от состояния:
```text
Подать заявку
        ↓
Заявка отправлена
        ↓
Участие подтверждено
        ↓
Войти в игру
```

Не следует показывать пользователю действия, которые ему недоступны.

---

# 11. Team Page

Страница команды должна быть простой и информативной.

Основная информация:

* название;
* капитан;
* участники;
* статистика;
* история игр.

Для капитана дополнительные действия отображаются не в отдельном интерфейсе, а внутри того же экрана.

Например:
```text
Команда
─────────────────────────
Аннигиляторная пушка

Капитан: ...

Участники
─────────
...
...
...

[Управление командой]
```

Обычный участник кнопку управления не видит.

---

# 12. Profile

Профиль должен восприниматься как персональная страница игрока.

Основные блоки:
```text
Профиль
─────────────
Основная информация

Статистика
─────────────
Количество игр
Победы
Финиши
...

История игр
─────────────
...

Авторство
─────────────
...
```

Статистика должна быть компактной и визуально легко считываться.

---

# 13. Author UI

Авторская часть может быть визуально более информационно насыщенной, чем пользовательская.

Основные разделы:

```
Предстоящие
Идущие
Завершённые
```

Редактор Quest должен позволять работать с квестом как с единым объектом.

Основные разделы редактора:

```
Настройки игры
Уровни (Описание, Коды, Подсказки)
Управление командами
Управление игрой
Статистика
```

---

# 14. Forms

Формы должны быть максимально простыми.

Правила:

* label всегда должен быть связан с полем;
* обязательные поля должны быть очевидны;
* ошибка отображается рядом с соответствующим полем;
* сообщение об ошибке должно объяснять проблему;
* не использовать alert для обычных ошибок валидации;
* submit должен иметь понятное название действия.

Например:
```text
Название квеста
[________________________]

Описание
[________________________]
[________________________]

Дата начала
[________________________]

              [Создать квест]
```

---

# 15. Buttons

Используются три основных уровня:

## Primary

Главное действие страницы.

Примеры:
* Создать квест
* Подать заявку
* Войти в игру
* Сохранить


## Secondary

Второстепенное действие.

Примеры:
* Отмена
* Подробнее
* Статистика


## Destructive

Опасное или необратимое действие.

Примеры:
* Удалить
* Отклонить

Destructive actions должны по возможности требовать подтверждения.

---

# 16. Tables

Таблицы используются прежде всего в:
* статистике игры;
* административных разделах;
* списках команд;
* списках кодов;
* списках уровней.

Таблицы должны:
* хорошо читаться на desktop;
* адаптироваться к мобильному экрану;
* визуально выделять активную строку;
* не содержать лишних колонок.

---

# 17. Game Mode

Игровой режим является отдельным визуальным контекстом.

Это наиболее важная часть UX QuestEngine.

Игрок во время игры не должен видеть обычный интерфейс приложения.

Игровой экран должен максимально быстро отвечать на вопрос:

> Что нам сейчас делать?

Основной layout:
```text
┌──────────────────────────────┐
│ Ночной дозор        01:23:45 │
├──────────────────────────────┤
│                              │
│ LEVEL 3                      │
│                              │
│ Найдите объект...            │
│                              │
│                              │
│ Код                          │
│ [____________________]       │
│                              │
│        [Ввести код]          │
│                              │
│ Подсказки                    │
└──────────────────────────────┘
```

---

# 18. Timer

Таймер является одним из основных элементов игрового интерфейса.

Он должен показывать оставшееся время текущего уровня.

Состояния:

```
Нормальное
↓
Мало времени
↓
Критическое
↓
Автопереход
```

Таймер не должен использовать агрессивную анимацию.

При приближении автоперехода визуальная индикация может становиться более заметной.

После автоперехода интерфейс должен максимально быстро перейти на следующий уровень и явно показать, что уровень завершён автоматически.

---

# 19. Code Input

Поле ввода кода является основным интерактивным элементом игрового режима.

Должно корректно отображаться и быть максимально доступным в один тап /клик для ввода кода.

Должно быть максимально отзывчивым. Ввод кода должен происходить по кнопке интерфейса или по нажатию "Ввод" на клавиатуре. 

Требования:
* максимально быстрое открытие клавиатуры на мобильном устройстве;
* крупное поле ввода;
* очевидная кнопка отправки;
* возможность быстро повторить ввод;
* мгновенная визуальная реакция.

После отправки:
```text
Правильный код
→ Success

Неправильный код
→ Error

Повторный ввод
→ Duplicate
```

История отправленных кодов отображаться, но это не мешает игровому процессу.

---

# 20. Level Transition

Переход между уровнями должен быть максимально быстрым.

После завершения уровня:

```
Level completed
        ↓
Next Level
```

Не требуется возвращать пользователя на страницу Quest.

Если уровень завершён автопереходом, следующий уровень также открывается непосредственно в игровом интерфейсе.

---

# 21. Finish Screen

После завершения последнего уровня:
```text
Квест завершён

Команда:
Аннигиляторная пушка

Время:
01:42:31

Место:
2
```

Точный набор отображаемых данных будет определён после проектирования статистики.

Главное:

* команда должна однозначно понимать, что игра закончена;
* нельзя случайно продолжить прохождение;
* должна быть доступна статистика игры.

---

# 22. Statistics UI

Статистика игры доступна уже после старта Quest.

Во время игры она показывает предварительное положение команд.

После завершения становится финальной.

Основное представление:
```text
    Level 1        Level 2         Level 3        Level 4      Итоги
1   Team A         Team B         Team A         -            1 Team B
2   Team B         Team A         Team B         Team B       2 Team A
3   Team C         Team C         -              -            3 Team C
```
Где:
> <Level #> - Название / номер уровня в игре. Все уровни это самая первая строка.

> <Team #> - Мини карточка команды с информацией:
> * Название команды
> * Имя (логин) игрока, который ввел код благодаря которому уровень был пройден командой или слово "автопереход"
> * Дата/время вплоть до 10 миллисекунд - когда был введен код благодаря которому уровень был пройден командой или время наступления автоперехода
> * Время с точностью до секунд - которое команда потратила на прохождение уровня
> * Бонусное/штрафное время полученное командой на уровне


Позиция команды определяется игровыми правилами, а frontend только визуализирует полученные данные.

Frontend не должен самостоятельно вычислять победителя.

---

# 23. Responsive Design

QuestEngine проектируется прежде всего как web application, но игровой режим должен быть mobile-first.

Приоритет:
```text
Game Mode:
Mobile > Tablet > Desktop

Обычный UI:
Mobile = Desktop
```

На мобильном устройстве:
* кнопки должны быть удобными для touch;
* поля ввода должны быть крупными;
* важная информация должна находиться в верхней части экрана;
* таблицы должны иметь адаптированное представление;
* горизонтальный scroll допускается только там, где без него невозможно сохранить структуру данных.

---

# 24. Accessibility

Frontend должен соблюдать базовые требования accessibility.

Минимально:

* семантический HTML;
* keyboard navigation;
* visible focus;
* labels для form controls;
* достаточный контраст;
* не полагаться только на цвет;
* aria-label для icon-only buttons;
* понятные сообщения об ошибках.

---

# 25. Animation

Анимация используется только там, где она помогает понять изменение состояния.

Допустимые случаи:
* появление нового уровня;
* успешный ввод кода;
* ошибка;
* изменение статуса;
* открытие / закрытие панели.

Не использовать постоянные декоративные animations.

Особенно важно избегать лишней анимации в игровом режиме.

---

# 26. Dark Mode

Приложение должно быть спроектировано с возможностью поддержки light и dark themes.

Переключение темы не должно требовать изменения компонентов.

Все цвета должны использовать semantic tokens.

Использование CSS variables позволяет централизованно менять тему.
