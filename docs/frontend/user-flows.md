# Frontend User Flows

## 1. Главная

```text
Пользователь
    │
    ▼
Главная
    │
    ├── Текущие квесты
    │       │
    │       └── Открыть квест
    │
    └── Предстоящие квесты
            │
            └── Открыть квест
```

Главная должна позволять быстро понять:
- какие игры идут сейчас;
- какие игры скоро начнутся;
- в каких играх пользователь/его команда участвует.

## 2. Участие в квесте
```text
Главная
   │
   ▼
Quest
   │
   ▼
Подать заявку
   │
   ▼
Ожидание подтверждения автора
   │
   ├── Отказаться
   │
   └── Автор подтвердил
            │
            ▼
       Ожидание старта
            │
            ▼
       Квест начался
            │
            ▼
       Войти в игру
            │
            ▼
       QuestProgress

```

Команда не начинает игру в момент подачи заявки.
Команда должна быть подтверждена автором.
После подтверждения команда ожидает начала Quest.

## 3. Вход в игру
```text
Quest стартовал
      │
      ▼
Команда открывает игру
      │
      ▼
GET current QuestProgress
      │
      ▼
GET current LevelProgress / related state
      │
      ▼
Отображение текущего состояния
      │
      ▼
Подключение realtime-канала
      │
      ▼
Подписка на разрешённые события
```

Игровое время начинается в установленное время старта Quest.

Момент, когда команда фактически нажала "Войти в игру", не переносит начало
соревнования.

Команда может войти позже и продолжить игру с учётом уже прошедшего времени.

REST используется для получения начального и актуального состояния.
Realtime-канал используется для уведомления об изменениях состояния без
polling. Backend остаётся источником истины.

## 4. Прохождение уровня
```text
LevelProgress ACTIVE
       │
       ├── Ввести код
       │      │
       │      ├── правильный
       │      │
       │      ├── неправильный
       │      │
       │      └── duplicate
       │
       ├── Использовать подсказку
       │
       └── Наступил autoTransitionAt
                    │
                    ▼
             AUTO_TRANSITIONED
```

Уровень может завершиться:

1. после достижения необходимого количества правильных кодов;
2. посредством автоперехода.

Неправильный ввод кода не удаляется.
Submission сохраняется как история попытки.

При изменении состояния backend может отправить realtime event. Frontend
отображает полученное состояние и не принимает самостоятельное решение о
завершении уровня.

## 5. Переход между уровнями

После завершения LevelProgress backend определяет наличие следующего
уровня.
```text
LevelProgress завершён
       │
       ▼
Есть следующий Level?
       │
       ├── Да
       │    │
       │    ▼
       │  Новый LevelProgress
       │
       └── Нет
            │
            ▼
       QuestProgress FINISHED
```

Frontend не принимает решение о наличии следующего уровня.

Frontend отображает состояние, полученное от backend.

Realtime event может уведомить frontend о завершении текущего уровня или
автопереходе. После события frontend использует новый authoritative state,
а не создаёт следующий LevelProgress самостоятельно.

## 6. Таймер уровня

Для первого уровня время автоперехода может зависеть от глобального
времени старта Quest.

Для последующих уровней timeout отсчитывается от фактического открытия
уровня командой, то есть от перехода на этот LevelProgress (см. документацию
по backend).

Пример:
Quest start:       21:00
Level 1 timeout:   60 min
Команда вошла:     21:40

Команда получает оставшееся время первого уровня.

Если команда завершила Level 1 в:
21:50

a Level 2 имеет:
timeout = 20 min

то:
Level 2 autoTransitionAt = 22:10

Frontend отображает таймер на основании серверного autoTransitionAt.

Realtime не используется для передачи countdown каждую секунду.
Frontend самостоятельно обновляет визуальный countdown, а backend
определяет фактический момент автоперехода.

## 7. Завершение игры
```text
Последний LevelProgress
       │
       ├── завершён кодами
       │
       └── завершён автопереходом
                │
                ▼
        QuestProgress FINISHED
```

Последний уровень не имеет особой игровой механики.

Он подчиняется тем же правилам, что и остальные уровни.

После изменения состояния backend может отправить `QUEST_FINISHED`.
Frontend отображает финальное состояние, полученное от backend.

## 8. Статистика

Статистика доступна сразу после начала игры.

```text
Quest
 │
 ▼
Statistics
 │
 ├── команды
 ├── уровни
 ├── порядок прохождения
 └── текущий результат
```

Во время игры статистика является предварительной.

После завершения игры она становится итоговой.

Итоговая позиция учитывает:
- время прохождения;
- бонусное время;
- штрафное время.

Live-изменения статистики могут доставляться через realtime-канал.
Frontend обновляет тот же server state, который используется для обычной
загрузки статистики.

## 9. Игровой UX

Игровой экран должен минимизировать количество действий между:
```text
получить задание
      ↓
решить
      ↓
ввести код
      ↓
получить результат
      ↓
продолжить
```

Обычная навигация приложения во время игры не используется.

Главный приоритет:
- скорость;
- читаемость;
- минимальное количество кликов;
- удобство мобильного использования.

При временной потере realtime-соединения интерфейс должен показать состояние
соединения, если это влияет на игровой UX. Потеря realtime не должна сама
по себе изменять состояние игры.

## 10. Realtime connection lifecycle

```text
Вход в Game Mode
      │
      ▼
Получить authoritative state через REST
      │
      ▼
Подключить realtime
      │
      ▼
Подписаться
      │
      ├── event → обновить server state / refetch
      │
      └── disconnect
              │
              ▼
          reconnect
              │
              ▼
       восстановить subscriptions
              │
              ▼
       при необходимости refetch
```

Reconnect не должен повторять пользовательские команды.
Идемпотентность пользовательских mutations определяется backend API-контрактом.
