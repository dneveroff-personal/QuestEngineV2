# Scheduling — автоматизация по времени

Статус: 🟡 Draft. Описывает механизм, который **полностью отсутствует** в текущей кодовой базе — ни одного `@Scheduled`, ни одного планировщика в проекте нет. Этот документ должен быть закрыт ADR перед началом реализации.

## Назначение

В движке есть два независимых процесса, управляемых **временем**, а не действием пользователя — то, что в описании Encounter называется «игра идёт сама», без нажатия кнопок:

1. **Старт Quest** — переход `REGISTRATION → RUNNING` в момент `Quest.startTime`.
2. **Автопереход уровня** — переход `LevelProgress.ACTIVE → AUTO_TRANSITIONED` в момент `LevelProgress.autoTransitionAt`.

Оба процесса должны срабатывать **без участия автора или команды** — иначе вся идея честного игрового времени (ADR-002) не работает.

---

## Текущее состояние реализации (важно)

Проверка кода на момент написания документа показала:

- В проекте нет ни одного `@Scheduled`, `TaskScheduler`, ShedLock или любого другого механизма отложенного/периодического выполнения.
- `QuestServiceImpl` не содержит **вообще никакого** метода перехода статуса Quest — ни автоматического, ни ручного. Это значит, что даже **шаг 3 «Публикация»** из `02-processes/quest-lifecycle.md` (`DRAFT → REGISTRATION`, ручное действие автора) не реализован: нет контроллера/эндпоинта для смены статуса. Quest создаётся и навсегда остаётся в `DRAFT`.
- Метод `QuestProgressServiceImpl.createProgress(questId, teamId)` уже существует и уже содержит нужные проверки (Quest должен быть `RUNNING`, регистрация `APPROVED`, защита от дубликата) — но **ничего его не вызывает** для случая массового старта. Он вызывается только из `QuestRegistrationServiceImpl.approveTeam()`, и только для случая «подтверждение после старта» (когда Quest уже `RUNNING`). Для случая «подтверждена заранее, Quest стартует по расписанию» — вызывающего кода нет.

Вывод: `createProgress()` уже спроектирован как строительный блок для планировщика — реализация планировщика должна использовать именно его, не дублируя логику.

## Блокер вне scope этого документа

Ручной переход `DRAFT → REGISTRATION` (кнопка «опубликовать Quest» у автора) — это не задача планировщика, это обычный CRUD-эндпоинт, которого не хватает. Зафиксировано в `roadmap/backlog.md` отдельным пунктом, т.к. без него `REGISTRATION` недостижим в принципе, и планировщику Quest start будет нечего стартовать.

## Job 1 — Quest Start

### Триггер
`Quest.status == REGISTRATION AND Quest.startTime <= now()`.

### Действие
1. Перевести Quest в `RUNNING`.
2. Для каждой `QuestRegistration` со статусом `APPROVED` по этому Quest — вызвать `questProgressService.createProgress(questId, teamId)`.

### Что job **не делает** (важное расхождение с ADR-002, требующее решения)

`ADR-002-quest-start-is-global.md` (текущий статус: **Accepted**) описывает, что в момент старта движок «открывает первый LevelProgress» и «запускает таймер первого уровня» — то есть подразумевает **eager**-создание `LevelProgress` для всех подтверждённых команд сразу при старте Quest.

Это прямо противоречит:
- `01-domain/progress.md`: «Первый LevelProgress создаётся в момент первого входа команды в Quest. Создание QuestProgress и создание первого LevelProgress являются разными событиями.»
- фактической реализации: `QuestProgressServiceImpl.enterQuest()` — единственное место, вызывающее `levelProgressService.createFirstLevelProgress(...)`, и вызывается оно только по явному действию команды («войти в квест»), не планировщиком.

**Рекомендация**: скорректировать ADR-002 (dependent ADR или явная правка) в пользу модели **progress.md** — ленивое создание `LevelProgress` при входе команды, а не при старте Quest. Причины:
- Не нужно создавать «мёртвые» строки `LevelProgress` для команд, подтверждённых, но так и не зашедших в игру (неявка, DNF с самого начала).
- Честность игрового времени **не зависит** от момента создания строки `LevelProgress` — она уже обеспечена тем, что `autoTransitionAt` для первого уровня считается от `Quest.startTime` (`QuestProgress.questStartedAt`), а не от `LevelProgress.openedAt`. Это правило уже зафиксировано в `progress.md` и не требует eager-создания для соблюдения ADR-002.
- Eager-модель требует, чтобы Job 1 создавал `LevelProgress` пачкой для потенциально сотен команд синхронно в одной транзакции планировщика — лишняя нагрузка и более крупная единица отказа (см. Job 1 идемпотентность ниже), тогда как ленивая модель размазывает эту нагрузку по времени входа команд.

Формулировка ADR-002 **сохраняется в актуальном виде для всего остального** (глобальность старта, отсутствие преимущества позднего входа) — меняется только конкретный технический пункт про eager-создание `LevelProgress`.

### Идемпотентность

Job может быть запущен повторно (ретрай после сбоя, дублирующий запуск при переразвёртывании) — переход статуса и создание прогресса должны быть безопасны при повторном выполнении:

- Переход статуса — через условный UPDATE (`UPDATE quests SET status='RUNNING' WHERE id=? AND status='REGISTRATION'`), а не через read-then-write в коде сервиса, чтобы конкурентные вызовы не перезаписывали друг друга бессмысленно.
- Создание `QuestProgress` — уже защищено существующей проверкой `validateNoDuplicateProgress` (упирается в уникальный индекс `(quest_id, team_id)` из `V11__create_quest_progress_table.sql`) — повторный вызов для уже обработанной команды безопасно завершится без дублирования (нужно только не давать этой ситуации всплывать как необработанное исключение, если Job перезапускается — обрабатывать как "уже сделано, пропустить").

## Job 2 — Level Auto-Transition

### Триггер
`LevelProgress.status == ACTIVE AND LevelProgress.autoTransitionAt <= now()`.

### Действие
1. Перевести `LevelProgress` в `AUTO_TRANSITIONED`, зафиксировать `completedAt`.
2. Если есть следующий `Level` (по `orderIndex`) — создать для него новый `LevelProgress` для этой же команды, с `openedAt = now()` и рассчитанным `autoTransitionAt = openedAt + Level.autoTransition` (см. `progress.md`, правило для «последующих» уровней).
3. Если следующего `Level` нет (это был последний уровень Quest) — см. открытый вопрос ниже.

### Открытый вопрос: что происходит с QuestProgress, если команда НЕ прошла последний уровень, а он завершился по автопереходу

`progress.md` описывает завершение `QuestProgress` статусом `FINISHED` «после прохождения последнего уровня» — но не уточняет: относится ли это только к прохождению **кодами** (`CODES`), или включает и случай, когда последний уровень завершился по `AUTO_TRANSITION` (то есть команда не успела/не смогла ввести коды вовремя).

Текущий код (`finishProgress()`) требует **ручного вызова автором** и не привязан к событию завершения уровня — значит, на практике сейчас QuestProgress не переходит в FINISHED автоматически ни в каком случае, только уполномоченным действием автора.

**Требуется решение** (одно из):
- **Вариант A**: `QuestProgress` завершается автоматически (`FINISHED`, если последний уровень пройден кодами; либо остаётся `RUNNING` до финального решения автора, если последний уровень истёк по таймеру, — то есть команда физически не прошла игру, и её судьбу решает автор — `FINISHED` вручную не выставляется, только `DNF` в конце Quest).
- **Вариант B**: `QuestProgress` завершается автоматически в обоих случаях (кодами или автопереходом) — автопереход последнего уровня трактуется как «время вышло, попытка окончена», финализация происходит сама.

**Рекомендация**: Вариант A — различие между «дошла своими силами» и «не успела» важно для статистики и честности результата (в Encounter-подобных играх факт непрохождения последнего уровня обычно фиксируется отдельно от факта честного финиша). Требует ADR перед реализацией Job 2 полностью (Job 2 логика для непоследних уровней не зависит от этого решения и может разрабатываться уже сейчас).

### Идемпотентность

Аналогично Job 1: переход статуса через условный UPDATE (`WHERE status='ACTIVE'`), создание следующего `LevelProgress` защищено уникальным индексом `(quest_progress_id, level_id)` (`V12__create_level_progress_table.sql`).

## Механизм выполнения

### Рекомендация для MVP: периодический polling-job

`@Scheduled(fixedDelay = ...)` в Spring — простейший вариант, не требует внешней инфраструктуры (очередей, брокеров), укладывается в уже выбранный стек (Spring Boot). Для масштаба «десятки одновременных Quest, сотни команд» — достаточно.

Альтернативы, рассмотренные и отклонённые для MVP:
- **Точный таймер на каждое событие** (`ScheduledExecutorService.schedule(delay)` на каждый `Quest.startTime`/`autoTransitionAt`) — даёт точность до миллисекунд, но требует пересчёта таймеров при редактировании (сдвиг `startTime`, `autoTransition`) и не переживает перезапуск инстанса без восстановления из БД при старте. Усложняет реализацию непропорционально выгоде на данном масштабе.
- **Очередь отложенных сообщений** (например, через брокер с delay-delivery) — правильное решение для по-настоящему большого масштаба, но избыточная инфраструктура для текущей стадии проекта.

### Точность (нужно решение в NFR)

Интервал polling — компромисс между нагрузкой на БД и задержкой срабатывания. Например, интервал 2–5 секунд даёт максимальную задержку срабатывания того же порядка — этого достаточно для честной игры (полсекунды-другая не даёт заметного преимущества), но конкретное число должно быть зафиксировано как NFR, а не выбрано произвольно в коде.

### Множественные инстансы приложения (важно для продакшена)

Если приложение развёрнуто в нескольких экземплярах (что typично для отказоустойчивости), **каждый** экземпляр будет пытаться выполнить один и тот же polling-job одновременно — без защиты это создаёт состояние гонки (см. также `02-processes/concurrency-scenarios.md`).

**Требуется распределённая блокировка.** Рекомендация: библиотека **ShedLock** (`net.javacrumbs.shedlock`) поверх уже используемого PostgreSQL — не требует дополнительной инфраструктуры (Redis/Zookeeper), лочит через таблицу в той же БД. Она же успешно комбинируется с идемпотентными UPDATE-запросами из Job 1/Job 2 как второй уровень защиты (defense in depth — блокировка не должна быть единственной линией обороны от дублирования).

Если MVP разворачивается в единственном экземпляре, ShedLock можно отложить, но идемпотентность самих job (условные UPDATE) должна быть реализована сразу — она защищает и от одиночных ретраев, и заранее готовит код к горизонтальному масштабированию.

## Открытые вопросы (требуют решения до реализации)

1. Правка ADR-002: убрать eager-создание `LevelProgress` при старте Quest, оставить только создание `QuestProgress` (см. выше — рекомендация дана).
2. Автоматическое завершение `QuestProgress` при прохождении последнего уровня — Вариант A/B (рекомендация: A).
3. Конкретный интервал polling — зафиксировать в `06-nfr/requirements.md` при заполнении этого раздела.
4. Нужен ли ShedLock уже в MVP, или откладывается до первого multi-instance деплоя — зависит от инфраструктурных планов, вне scope доменной документации.
5. Эндпоинт «опубликовать Quest» (`DRAFT → REGISTRATION`) отсутствует — блокер, зафиксирован в `roadmap/backlog.md`, не относится напрямую к планировщику, но должен быть закрыт в той же итерации.
