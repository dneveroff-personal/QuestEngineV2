# ADR-0015 — JWT Revocation Via Denylist

## Status

Accepted

## Context

JWT в текущей реализации — чистый stateless-токен со временем жизни 24 часа; сервер не хранит список выданных/отозванных токенов. Прямо сейчас нет способа принудительно разлогинить конкретного пользователя раньше истечения токена (например, при обнаружении читерства посреди игры) без смены `jwt.secret` глобально (что разлогинивает всех пользователей системы, а не одного). Полный разбор — `05-security/threat-model.md`, Находка 1.

## Decision

Внедряется **denylist отозванных токенов**: при административном отзыве (смена пароля, ручной бан) `jti` (JWT ID) токена добавляется в хранилище отозванных идентификаторов с TTL, равным оставшемуся времени жизни токена (не более 24 часов — не требует бессрочного хранения). `JwtAuthFilter` дополнительно проверяет `jti` против этого хранилища при каждой валидации токена.

Хранилище — таблица в существующей PostgreSQL (не требует новой инфраструктуры вроде Redis на этом масштабе; см. также выбор ShedLock через PostgreSQL в `03-architecture/scheduling.md` — согласованный подход, не заводить новую БД-технологию ради одной фичи).

## Consequences

Преимущества:
- Появляется техническая возможность немедленно отозвать доступ конкретного пользователя — важно для соревновательной честности (бан читера посреди игры), не только для безопасности в общем смысле.
- Низкая стоимость реализации: TTL ограничен временем жизни токена, таблица не растёт неограниченно.

Издержки:
- Каждая валидация токена требует дополнительного обращения к БД (или кэшу) — незначительно на ожидаемых объёмах (см. `06-nfr/requirements.md`), но стоит вынести под общий пересмотр, если нагрузка окажется выше ожидаемой.
