# ADR-0005 — Level Is Completed By Any Single MAIN Code

## Status

Proposed — затрагивает игровой дизайн, требует подтверждения продукта перед реализацией `CodeSubmission`.

## Context

`01-domain/progress.md` описывает завершение уровня как «команда ввела необходимое количество правильных кодов» — формулировка не даёт однозначного критерия, а модель данных `Level` не содержит поля вроде `requiredMainCodesCount`.

Два возможных прочтения (полный разбор — `01-domain/code-submission.md`):

- **Вариант A**: у уровня может быть несколько `MAIN`-кодов — это синонимы одного правильного ответа. Достаточно ввести любой один, чтобы завершить уровень.
- **Вариант B**: уровень требует ввода всех `MAIN`-кодов (составная загадка из нескольких частей).

Вариант A соответствует классической механике Encounter (один ответ, несколько принятых написаний/синонимов) и не требует дополнительного состояния в `LevelProgress` (сравнить с Вариантом B, где нужно хранить, какие именно `MAIN`-коды из набора уже введены).

## Decision

Принимается **Вариант A**: ввод любого одного `MAIN`-кода, принадлежащего активному Level команды, завершает уровень.

Если автору требуется загадка из нескольких частей (Вариант B) — это моделируется не одним Level с несколькими обязательными кодами, а несколькими последовательными Level (или через будущую отдельную фичу «составной уровень», не входящую в MVP).

## Consequences

Преимущества:
- Простая модель `LevelProgress` — не нужно отслеживать частичный прогресс ввода кодов внутри одного уровня.
- Прямое соответствие уже принятой модели `CodeType` (MAIN/BONUS/PENALTY) — множественность MAIN-кодов уже выразима без изменения схемы.

Издержки:
- Авторы, которым нужна составная загадка «несколько частей на одном экране», должны будут смоделировать это через несколько уровней — менее гибко, чем явная поддержка Варианта B. Признаётся как сознательный компромисс ради простоты MVP.

**Требует подтверждения продукта до реализации `CodeSubmission`** — если игровой дизайн предполагает составные загадки как частый случай, решение нужно пересмотреть до, а не после реализации.
