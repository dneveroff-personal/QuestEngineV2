# ADR-0002 — Quest Start Is Global

## Status

Accepted

## Context

Quest имеет заранее определённое время начала.

В момент старта соревнования все команды должны находиться в одинаковых условиях.

Время прохождения зависит исключительно от времени старта Quest, а не от момента открытия приложения игроками.

Это полностью соответствует механике игр семейства Encounter.

## Decision

В момент наступления времени начала Quest считается стартовавшим независимо от действий игроков.

Движок автоматически:

- переводит Quest в состояние RUNNING;
- создаёт QuestProgress для всех зарегистрированных (APPROVED) команд.

`LevelProgress` первого уровня **не** создаётся eager-но для всех команд в этот момент — он создаётся лениво, в момент первого входа команды в Quest (`enterQuest()`). Честность игрового времени при этом не страдает: таймер автоперехода первого уровня (`autoTransitionAt`) считается от `QuestProgress.questStartedAt` (момент старта Quest), а не от момента создания `LevelProgress` — поэтому позднее фактическое создание строки в БД не даёт позднему входу никакого преимущества.

Если команда открывает приложение позже, она получает уже идущий отсчёт первого уровня — вплоть до немедленного `AUTO_TRANSITIONED`, если команда вошла уже после истечения времени автоперехода первого уровня.

## Example

```
21:00:00

Quest started

↓

QuestProgress(Team A) создан
QuestProgress(Team B) создан
QuestProgress(Team C) создан

(LevelProgress ещё не существует ни для одной команды)

↓

21:05

Team B открывает приложение → enterQuest()

↓

Создаётся первый LevelProgress(Team B),
autoTransitionAt считается от 21:00:00 (не от 21:05) —
если время автоперехода уже прошло, уровень сразу AUTO_TRANSITIONED.
```

## Consequences

Преимущества:

- отсутствует преимущество позднего входа — обеспечивается расчётом `autoTransitionAt` от времени старта Quest, а не моментом создания `LevelProgress`;
- единая временная шкала для всех участников;
- простая реализация таймеров;
- прозрачная статистика;
- полное соответствие правилам соревнования;
- движок не создаёт «мёртвые» строки `LevelProgress` для команд, подтверждённых, но не зашедших в игру (неявка/DNF с самого начала);
- нагрузка от создания `LevelProgress` размазана по времени фактического входа команд, а не сконцентрирована в одной пачке в момент старта Quest.

Издержки: нет — отказ от eager-создания `LevelProgress` не ослабляет ни одно из исходных свойств решения (глобальность старта, честность времени), только упрощает реализацию.

Реализация: `03-architecture/scheduling.md` (Job 1 — создание QuestProgress по расписанию), `QuestProgressServiceImpl.enterQuest()` (ленивое создание первого LevelProgress, уже реализовано в коде).
