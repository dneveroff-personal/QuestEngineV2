# ADR-0015 — Access + Refresh Token Pattern

## Status

Accepted — заменяет первоначальный вариант («простой JWT + denylist»), отклонённый в пользу более стандартного для индустрии паттерна (осознанный учебный выбор — см. `00-vision/product-vision.md`, учебные цели проекта).

## Context

Первоначальный вариант этого ADR предлагал единый JWT на 24 часа с denylist отозванных токенов для случая досрочного отзыва (см. `05-security/threat-model.md`, Находка 1). Владелец продукта предпочёл более распространённый в индустрии паттерн — пару access+refresh токенов — как учебную цель проекта (освоить современный стек так, как это делается на практике).

## Decision

Аутентификация выдаёт **два токена**:

- **Access token** — JWT, короткое время жизни (**15 минут**), используется для авторизации каждого API-запроса (`Authorization: Bearer`), как и раньше. Полностью stateless — `JwtAuthFilter` не обращается к БД/кэшу при каждой проверке (в отличие от отклонённого варианта с denylist).
- **Refresh token** — используется только для получения нового access-токена через `POST /auth/refresh`. Хранится **в БД** (таблица `refresh_tokens`: `id`, `user_id`, `token_hash` — хеш, не сырое значение, `issued_at`, `expires_at`, `revoked_at`, `replaced_by_token_id`). Время жизни — существенно дольше access-токена (например, 30 дней).

**Ротация refresh-токена**: при каждом обращении к `/auth/refresh` старый refresh-токен помечается отозванным (`revoked_at`), выдаётся новый (`replaced_by_token_id` указывает на него) — классическая защита от повторного использования украденного refresh-токена (reuse detection: если отозванный токен предъявлен повторно — это сигнал компрометации, все refresh-токены пользователя отзываются немедленно).

**Отзыв доступа пользователя** (административный бан, смена пароля, logout): помечаются отозванными все активные `refresh_tokens` этого пользователя. Access-токен, уже выданный до отзыва, продолжит действовать **не дольше 15 минут** (естественное истечение) — это принятая, явно задокументированная задержка отзыва, значительно короче прежних 24 часов.

## Consequences

Преимущества:
- Access-токен полностью stateless — `JwtAuthFilter` не требует обращения к БД на каждый запрос (в отличие от отклонённого denylist-варианта, где каждая проверка требовала бы lookup).
- Задержка отзыва сокращена с 24 часов до 15 минут — без цены в виде БД-запроса на каждый API-вызов.
- Ротация refresh-токена с reuse detection — общепринятая практика, соответствует учебной цели «пощупать» современный стек так, как это делается в индустрии.
- Logout становится содержательной операцией (отзыв refresh-токена), а не no-op, как было бы с чистым stateless JWT.

Издержки:
- Требуется новая таблица `refresh_tokens` (миграция схемы) и новый эндпоинт `POST /auth/refresh`.
- Клиент должен уметь обновлять access-токен по истечении 15 минут (интерцептор на 401 → refresh → повтор запроса) — усложнение клиентской логики по сравнению с единым долгоживущим токеном.
- Компрометация refresh-токена опаснее компрометации access-токена (даёт долгосрочный доступ) — компенсируется хранением только хеша в БД (аналогично паролю) и ротацией.
