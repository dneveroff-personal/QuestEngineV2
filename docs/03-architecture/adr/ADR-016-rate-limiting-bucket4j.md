# ADR-0016 — Rate Limiting Via bucket4j

## Status

Accepted

## Context

Поиск по кодовой базе и `build.gradle.kts` не нашёл ни одной библиотеки или собственной реализации для ограничения частоты запросов. Уязвимы как минимум: `POST /auth/login` (перебор паролей) и в перспективе — ввод кодов командой (`CodeSubmission`, короткие коды уязвимы к перебору). Полный разбор — `05-security/threat-model.md`, Находка 2; `01-domain/code-submission.md`.

## Decision

Внедряется **`bucket4j`** как единый механизм rate limiting для всего проекта — не заводить отдельные решения для `/auth/login` и для будущего ввода кодов.

Реализация — фильтр на уровне Spring Security (аналогично `JwtAuthFilter`), лимитирующий по комбинации IP + эндпоинт для анонимных запросов (`login`) и по `LevelProgress`/пользователю для аутентифицированных игровых действий (ввод кода). Хранилище состояния лимитера — in-memory (`bucket4j` поддерживает это из коробки) для single-instance деплоя; при переходе на multi-instance потребуется распределённое хранилище (согласуется с тем же решением, что и для ShedLock в `03-architecture/scheduling.md`).

Конкретные числа (сколько попыток за какой интервал) не фиксируются этим ADR — определяются отдельно при реализации `05-security/threat-model.md` и `01-domain/code-submission.md` для каждого конкретного эндпоинта.

## Consequences

Преимущества:
- Стандартная, широко используемая в Spring-экосистеме библиотека, не требует написания собственного алгоритма ограничения.
- Единый механизм для всех будущих rate-limited эндпоинтов, а не разрозненные решения.

Издержки:
- In-memory состояние не переживает перезапуск/не синхронизируется между инстансами — приемлемо для текущего масштаба (см. `06-nfr/requirements.md`), потребует пересмотра при multi-instance деплое.
