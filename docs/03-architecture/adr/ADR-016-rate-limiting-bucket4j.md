# ADR-0016 — Rate Limiting Via bucket4j

## Status

Accepted

## Context

Поиск по кодовой базе и `build.gradle.kts` не нашёл ни одной библиотеки или собственной реализации для ограничения частоты запросов. Уязвим как минимум: `POST /auth/login` (перебор паролей). Полный разбор — `05-security/threat-model.md`, раздел «Rate Limiting».

**Важное уточнение (решение продукта)**: ввод кода командой (`CodeSubmission`) **намеренно исключён** из scope rate limiting — команда может состоять из десятков участников, вводящих коды параллельно, и скорость ввода — часть сути игры. Троттлинг здесь ограничивал бы легитимный геймплей. Защита от автоматизированного перебора кодов — не троттлингом, а аудитом попыток (см. `01-domain/code-submission.md`).

## Decision

Внедряется **`bucket4j`** для ограничения частоты запросов на аутентификационных эндпоинтах — в первую очередь `POST /auth/login` (5 попыток/минуту на IP).

Реализация — фильтр на уровне Spring Security (аналогично `JwtAuthFilter`), лимитирующий по IP для анонимных запросов. Хранилище состояния лимитера — in-memory (`bucket4j` поддерживает это из коробки) для single-instance деплоя; при переходе на multi-instance потребуется распределённое хранилище (согласуется с тем же решением, что и для ShedLock в `03-architecture/scheduling.md`).

`CodeSubmission` (ввод кода командой) этим решением не ограничивается — см. Context выше и `01-domain/code-submission.md`.

## Consequences

Преимущества:
- Стандартная, широко используемая в Spring-экосистеме библиотека, не требует написания собственного алгоритма ограничения.
- Единый механизм для всех будущих rate-limited эндпоинтов, а не разрозненные решения.

Издержки:
- In-memory состояние не переживает перезапуск/не синхронизируется между инстансами — приемлемо для текущего масштаба (см. `06-nfr/requirements.md`), потребует пересмотра при multi-instance деплое.
