# ADR-0010 — Pessimistic Locking For Confirmed Race Conditions

## Status

Accepted

## Context

Прочтение кода выявило две подтверждённые (не гипотетические) уязвимости класса read-then-write без блокировки — полный разбор в `02-processes/concurrency-scenarios.md`:

- **Сценарий 1**: `QuestRegistrationServiceImpl.approveTeam()` считает `countByQuestIdAndStatus(APPROVED)` и сравнивает с лимитом без блокировки — конкурентное подтверждение двух заявок на последнее место может превысить `maximumTeams`.
- **Сценарий 2**: `QuestProgressServiceImpl.enterQuest()` проверяет `status == WAITING` без блокировки перед созданием первого `LevelProgress` — конкурентный повторный вызов (двойной клик, ретрай сети) может привести к необработанному исключению нарушения ограничения БД вместо корректного идемпотентного ответа.

## Decision

**Сценарий 1**: `SELECT ... FOR UPDATE` на строку `Quest` перед подсчётом `APPROVED`-регистраций внутри `approveTeam()` — сериализует конкурентные подтверждения для одного и того же Quest. Выбрано вместо advisory lock и вместо триггера БД — самое простое и понятное решение, оправданное тем, что подтверждение заявок не является hot path (разовое административное действие автора, не сотни запросов в секунду).

**Сценарий 2**: создание первого `LevelProgress` оборачивается в обработку `DataIntegrityViolationException` (нарушение существующего `UNIQUE(quest_progress_id, level_id)`) — при перехвате возвращается уже существующий `LevelProgress`, трактуя повторный вызов как идемпотентный успех, а не ошибку.

Оба решения применяются как обязательный паттерн: любой новый метод, выполняющий проверку условия перед сохранением («count < limit», «status == X»), обязан быть либо защищён блокировкой уровня БД, либо спроектирован идемпотентно относительно конкурентного вызова — не полагаться только на проверку в коде сервиса.

## Consequences

Преимущества:
- Устраняет два подтверждённых бага без изменения публичного API.
- Формализует общий паттерн, применимый и к будущим `CodeSubmission`/`HintProgress` (см. `02-processes/concurrency-scenarios.md`, Сценарии 3 и 5).

Издержки:
- `SELECT ... FOR UPDATE` сериализует конкурентные `approveTeam()` для одного Quest — приемлемо, т.к. это редкое административное действие, не пользовательский hot path.

Каждое исправление обязано сопровождаться тестом, явно воспроизводящим гонку (параллельные потоки), а не только тестом на happy path — см. `07-quality/testing-strategy.md`.
