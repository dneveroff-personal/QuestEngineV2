# ADR-0017 — Minimum Test Coverage Threshold Enforced By Build

## Status

Accepted

## Context

JaCoCo уже подключён (`build.gradle.kts`, `tasks.jacocoTestReport`), генерирует отчёт, но не проваливает сборку при недостаточном покрытии — отчёт можно посмотреть, но регресс покрытия со временем ничем не предотвращён. Найдено при написании `07-quality/testing-strategy.md`.

## Decision

Добавляется `tasks.jacocoTestCoverageVerification`, привязанная к `check` (стандартной Gradle-задаче, выполняемой перед сборкой в CI), с порогом **70% line coverage** для пакетов `*.service` (сервисный слой, где сосредоточена бизнес-логика и куда, согласно уже устоявшемуся паттерну, пишутся `*ServiceImplTest`).

70% выбрано как стартовый порог — заведомо ниже текущего фактического покрытия (учитывая уже написанные тесты для всех существующих сервисов), чтобы задача не блокировала текущую сборку сразу при внедрении, но достаточно высок, чтобы ловить реальный регресс (например, добавление сервиса без единого теста). Порог пересматривается в сторону повышения после первого измерения фактического покрытия.

Пакеты `*.entity`, `*.dto`, `*.controller` не включаются в порог этим решением — controller-слой покрывается `*ControllerTest`/`*ControllerIT` (другой вид тестов, не покрывается line coverage сервисного слоя так же осмысленно), entity/dto — в основном данные без логики.

## Consequences

Преимущества:
- Регресс покрытия сервисного слоя проваливает сборку, а не остаётся незамеченным в отчёте.
- Порог явный и обсуждаемый (число зафиксировано здесь, а не выбрано произвольно при первом столкновении с проблемой).

Издержки:
- Может потребовать написания дополнительных тестов для существующих сервисов, если фактическое покрытие где-то ниже 70% — требуется первый прогон отчёта для проверки перед включением задачи в CI как обязательной.

Порог — стартовое значение, подлежит пересмотру, не финальное решение на все время жизни проекта.
