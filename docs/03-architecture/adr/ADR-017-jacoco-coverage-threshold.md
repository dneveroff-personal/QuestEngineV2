# ADR-0017 — JaCoCo Coverage Reports Without Build Gate

## Status

Accepted (amended)

## Context

JaCoCo уже подключён (`build.gradle.kts`, `tasks.jacocoTestReport`), генерирует HTML/XML-отчёты и публикует их как артефакт CI. Первоначально планировалось добавить `jacocoTestCoverageVerification` с жёстким порогом (70% line coverage сервисного слоя), который проваливал бы сборку при недостаточном покрытии.

Жёсткий порог и fail-the-build по покрытию для текущего этапа проекта (учебный MVP, активная эволюция API и домена) дают больше трения, чем пользы: заставляют писать тесты «ради процента», тормозят итерации и плохо сочетаются с осознанным Definition of Done (три уровня тестов на фичу), который уже дисциплинирует качество без числового gate.

## Decision

1. **JaCoCo остаётся** — `jacocoTestReport` после `test`, HTML/XML отчёты, выгрузка в CI как артефакт (как сейчас в `build.yml`).
2. **`jacocoTestCoverageVerification` не добавляется** — сборка **не** падает из-за процента покрытия.
3. **Числовой порог покрытия не фиксируется** в ADR и не используется как критерий merge/release.
4. Качество тестов обеспечивается паттерном из `07-quality/testing-strategy.md` (ServiceImplTest + ControllerTest + ControllerIT, concurrency-тесты где нужно, Clock-инъекция) и code review, а не процентом в отчёте.

Отчёт по-прежнему полезен: можно смотреть покрытие при ревью и локально (`./gradlew test jacocoTestReport`), но он информационный, не блокирующий.

## Consequences

Преимущества:
- Нет ложных блокеров CI из-за «недобрали до N%» при осмысленном покрытии критичных путей.
- Сохраняется видимость покрытия через отчёты и артефакты CI.
- DoD и трёхуровневый паттерн тестов остаются обязательными для новых фич.

Издержки:
- Регресс покрытия формально не ломает сборку — ответственность на ревью и дисциплине DoD.
- Если позже понадобится жёсткий gate (например, перед публичным релизом), это отдельное решение с новым порогом и явным включением verification-задачи.
