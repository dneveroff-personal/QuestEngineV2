# ADR-0014 — Server-Sent Events For Live Statistics

## Status

Accepted

## Context

`01-domain/statistics-ranking.md` требует автоматического обновления статистики при каждом изменении `QuestProgress`, но не указывает транспорт. Пакет `statistic/` в коде пуст — реализации нет вообще. Полный разбор вариантов — `06-nfr/requirements.md`.

Рассмотрены три варианта: polling, Server-Sent Events (SSE), WebSocket. Статистика — строго однонаправленный поток (сервер → клиент), клиент ничего не отправляет через тот же канал.

## Decision

Транспорт для live-статистики — **Server-Sent Events**.

Обоснование:
- Данные идут только в одну сторону — WebSocket даёт возможности (двусторонний канал), которые не требуются, ценой дополнительной инфраструктурной сложности (управление соединениями, реконнект, sticky sessions или pub/sub для multi-instance).
- Polling даёт либо заметную задержку отображения, либо лишнюю нагрузку на сервер при попытке её уменьшить частым опросом множества одновременных клиентов.
- SSE реализуется штатными средствами Spring MVC (`ResponseBodyEmitter`/`SseEmitter`) без дополнительных библиотек, укладывается в уже выбранный стек.

## Consequences

Преимущества:
- Минимальная дополнительная инфраструктурная сложность по сравнению с WebSocket.
- Ниже задержка отображения по сравнению с разумно частым polling, без лишней нагрузки от постоянного опроса.

Издержки:
- SSE не работает «из коробки» через некоторые прокси/балансировщики без явной настройки (буферизация должна быть отключена) — потребует внимания на этапе деплоя.
- Если в будущем потребуется двусторонний realtime-канал (например, для чего-то за пределами текущего scope) — потребуется отдельное решение, SSE не масштабируется в WebSocket без замены транспорта.

Решено: SSE отправляет обновление немедленно при каждом изменении `QuestProgress`, без искусственной задержки/батчинга — согласуется с общим приоритетом проекта на скорость (см. решение не троттлить ввод кода, `05-security/threat-model.md`). Отдельного числа "допустимой задержки" не требуется — задержка определяется только временем обработки события и сетью, не политикой батчинга.
