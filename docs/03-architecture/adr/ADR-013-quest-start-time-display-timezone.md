# ADR-0013 — Quest.startTime Is Always Displayed In The User's Device Timezone

## Status

Accepted

## Context

`Quest.startTime` хранится корректно (`Instant`, `TIMESTAMP WITH TIME ZONE` в PostgreSQL) — расчёты (автопереход, старт Quest) не зависят от часового пояса отображения, это не под вопросом. Открытым оставался только вопрос **отображения** времени пользователю — в поясе места проведения или в поясе устройства пользователя. Разбор — `06-nfr/requirements.md`.

ADR-0019 закрыл предпосылку этого вопроса: движок не различает офлайн/онлайн форматы структурно, поэтому нет оснований вводить разное поведение отображения для разных типов Quest.

## Decision

`Quest.startTime` (и любой другой пользовательский timestamp) всегда отображается **в часовом поясе устройства пользователя** — стандартное поведение браузера/клиентского приложения (`Intl.DateTimeFormat`/аналог на клиенте), без дополнительного поля часового пояса на Quest.

Расчёты на сервере остаются в UTC (`Instant`) без изменений — это решение касается только слоя представления.

## Consequences

Преимущества:
- Не требует нового поля в модели данных (`Quest.timezone` не нужен) — минимальное решение.
- Стандартное, ожидаемое пользователем поведение (как в большинстве современных приложений — время показывается «как удобно мне»).

Издержки:
- Для оффлайн-квестов, где физическое место проведения жёстко привязано к конкретному часовому поясу (например, если организатор и участник в разных городах координируют что-то по времени старта), участник должен сам учитывать разницу поясов при планировании явки на месте. Это признанный компромисс — автор Quest обязан явно указать место проведения и время в его контексте в описании/анонсе (текстовое содержание, не структурное поле), если это существенно для конкретной игры.

Реализуется полностью на клиенте — сервер не требует изменений сверх уже корректного хранения в `Instant`.
