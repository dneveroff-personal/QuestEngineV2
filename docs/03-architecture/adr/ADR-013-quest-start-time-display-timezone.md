# ADR-0013 — Quest.startTime Display Timezone

## Status

Proposed — заблокирован нерешённым продуктовым вопросом (см. ADR-0019).

## Context

`Quest.startTime` хранится корректно (`Instant`, `TIMESTAMP WITH TIME ZONE` в PostgreSQL) — расчёты (автопереход, старт Quest) не зависят от часового пояса отображения. Открытым остаётся только вопрос **отображения** времени пользователю.

Для оффлайн-квестов (команда физически перемещается по городу) время должно отображаться в часовом поясе места проведения — иначе показания разъедутся с реальностью на месте. Для онлайн-квестов (команда играет удалённо) логичнее показывать время в часовом поясе устройства игрока.

Это решение прямо зависит от ADR-0019 (целевая аудитория и формат игры — офлайн/онлайн), который пока не принят.

## Decision

**Решение не принято.** Документируется как заблокированное продуктовым вопросом, а не как техническая недоработка — реализация не должна начинаться до ADR-0019.

Технический вариант, который будет реализован после разблокировки (независимо от исхода ADR-0019, для справки):
- Если формат преимущественно оффлайн — добавить `Quest.timezone` (IANA-идентификатор, например `Europe/Moscow`), отображать `startTime` в этом поясе для всех участников независимо от их устройства.
- Если формат преимущественно онлайн — отображать `startTime` в часовом поясе устройства/браузера пользователя (стандартное поведение, дополнительных полей в модели не требуется).
- Если поддерживаются оба формата — понадобится оба механизма, выбор — по `QuestType`/новому полю формата игры.

## Consequences

Не применимо до принятия решения. Хранение в `Instant`/`TIMESTAMPTZ` остаётся правильным в любом из исходов — переработка потребуется только в слое отображения (DTO/frontend), не в модели данных.
