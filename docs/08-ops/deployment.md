# Deployment Topology

Статус: 🟢 Accepted.

## Назначение

Зафиксировать, как frontend и backend разворачиваются вместе — локально и
в проде. Закрывает открытый пункт из `05-security/threat-model.md`:

> Если позже появится отдельный фронтенд на отдельном домене — потребуется
> явный whitelist origin'ов... Это решается на этапе, когда конкретная
> схема деплоя фронтенда определится.

Этот документ и есть та точка решения.

---

## Решение

**Единая публичная точка входа — nginx.** Backend не публикуется в интернет
напрямую.

```text
                    Интернет
                        │
                        ▼
              ┌──────────────────┐
              │  nginx (frontend) │  :80
              │  статика + proxy  │
              └─────────┬─────────┘
                        │
          ┌─────────────┼─────────────┐
          │                            │
   отдаёт статику              proxy_pass
   (index.html, /assets/)      /api/* (включая /api/auth/*)
          │                            │
          ▼                            ▼
   собранный React SPA          app:8080 (Spring Boot)
                                        │
                                        ▼
                                  postgres:5432
```

Frontend и backend — **два независимых Docker-образа**, у каждого свой
`Dockerfile` и своя публикация в registry (`ghcr.io/.../questenginev2` и
`ghcr.io/.../questenginev2-frontend`). Собираются и версионируются
раздельно (`.github/workflows/build.yml` — отдельные job'ы, каждый
запускается только если менялась соответствующая часть репозитория).

Оба образа выкатываются на **один и тот же хост** через `docker-compose`,
за одним и тем же nginx — это то, что делает их same-origin с точки зрения
браузера, без единой строчки `CorsConfiguration` на backend.

## Почему не другие варианты

- **Frontend внутри backend-артефакта** (`dist/` как Spring static
  resources) — самый простой вариант, но связывает Java- и Node-сборку в
  одном пайплайне и лишает раздельного деплоя/отката. Отклонено — цель
  проекта именно в том, чтобы пощупать раздельный современный деплой.
- **Frontend на Vercel/Netlify** — нарушил бы уже принятое same-origin
  решение (`threat-model.md`), потребовал бы явный CORS whitelist на
  backend. Отклонено, чтобы не пересматривать принятое решение без
  необходимости.

## Локальная разработка

`npm run dev` (Vite dev-сервер, `localhost:5173`) и backend
(`localhost:8080`, отдельно) технически разные origin, даже на одной
машине. Same-origin из `threat-model.md` действует только за общим nginx
в проде — в dev-режиме это решено иначе: `vite.config.ts` содержит
`server.proxy` для `/api` (auth-эндпоинты живут внутри `/api/auth/*`, не
требуют отдельного правила), зеркалирующий маршрутизацию
`nginx.conf`. С точки зрения браузера запросы всё равно идут на
`localhost:5173`, Vite сам проксирует их на backend — CORS не нужен ни в
dev, ни в проде, ни на одном из двух уровней (Vite proxy и prod nginx)
конфигурация не должна расходиться, если у backend появится новый
префикс маршрутов — надо поправить оба файла.

Полный docker-compose стек (nginx + app + postgres, собранные как в
проде) также доступен локально:

```bash
docker compose -f docker-compose.local.yml up -d --build
# приложение: http://localhost:8081
# backend напрямую (для отладки/Swagger): http://localhost:8080
```

## SSE и nginx-буферизация

`nginx.conf` явно отключает буферизацию (`proxy_buffering off`) для
`/api/statistics/` — иначе nginx будет накапливать SSE-события в буфер
перед отправкой браузеру, что на практике превращается в задержку/батчинг,
который ADR-0014 прямо запрещает ("без искусственной задержки"). Это
единственный location с таким переопределением — везде больше buffering
по умолчанию корректен и даже полезен (обычные HTTP request/response).

## Прод

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

`app` в проде не публикует порт на хост (`expose`, не `ports`) — доступен
только внутри docker-сети как `app:8080`. Единственный открытый порт
хоста — `80` (frontend/nginx). Это не только реализует same-origin, но и
уменьшает открытую наружу поверхность.

## Открытые вопросы

- HTTPS/TLS — не в scope этого документа. При первом реальном деплое в
  интернет потребуется TLS-терминация (Let's Encrypt/Certbot перед nginx,
  либо Caddy вместо nginx, который делает это автоматически) — сейчас
  сознательно отложено до момента реального деплоя, не блокирует
  локальную и pre-prod работу.
- Версионирование frontend-образа сейчас читается из `package.json`
  (`"version": "0.0.0"`) — не синхронизировано с backend-версией
  (Gradle). Осознанно не синхронизируется: frontend и backend
  версionируются независимо, это следствие раздельного деплоя, а не
  недосмотр.
